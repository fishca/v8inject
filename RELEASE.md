Пакетный релиз по ревизии 2026-11-21 (docs/AUDIT.md §10): закрыты все
находки приоритетов P0/P1/P2 — 24 из 76. Тема релиза — безопасность кода,
живущего в чужом процессе: порча кучи 1С, заморозка потоков, дедлоки,
«вечная» занятость блока протокола, потеря ввода Конфигуратором. Состав
команд и JSON-протокол не менялись.

## Исправлено

**Нативное меню больше не портит кучу 1С.** Строки описаний команд, которые
payload кладёт во внутренние структуры платформы, уходили туда со счётчиком
ссылок 1: платформа освобождает такие блоки своим аллокатором (у payload и
1С разные CRT), и первый Release описания возвращал нашу память в чужую
кучу — отложенная порча кучи при закрытии конфигурации или перестроении
меню. Теперь счётчик равен 2: блок переживает Release и живёт до выхода из
процесса (те же ~24 байта на строку, что и у URL пунктов).

**Снятие хука из выгруженного модуля больше не замораживает 1С.** `unhook`
читал пролог цели под приостановкой всех потоков без проверки читаемости:
если модуль с хуком выгрузился (хук на плагин), чтение падало, SEH-раскрутка
не выполняла продолжение потоков — все потоки 1С оставались замороженными
навсегда, а на выходе payload это было падением процесса. Окно
восстановления теперь под стражем и SEH: нечитаемая цель — отказ снятия,
хук остаётся в списке, потоки продолжают работать.

**Параллельные установки хуков больше не спорят за приостановку.** Окно
«приостановить всё → пропатчить → продолжить» не было сериализовано:
командный цикл, воркер нативного меню и ранний воркер подписки могли войти
в него одновременно и приостановить друг друга — дедлок с замороженными
потоками 1С. Окно сериализовано: второй ждёт в kernel-space и продолжает
сразу после продолжения потоков первым.

**Кап записей в лог переживает 2 миллиарда вызовов.** Счётчик был знаковым:
после 2^31 вызовов горячего хука он переполнялся, и каждая запись хука снова
писала две строки в лог — flood и файловый I/O на потоке перехваченной
функции 1С. Кап теперь работает после оборота.

**Ответы `scan` больше не обрезаются и не убивают процесс.** `scan` был
единственной командой вне общего механизма ограничения ответов: ответ больше
блока резался посреди JSON-строки, а нехватка памяти завершала весь процесс
1С. Теперь `scan` под тем же SEH-кадром с ловлей `bad_alloc`, ответ
компактный, переполнение — честная ошибка «response too large»; в самом
протоколе обрезка заменена отказом.

**`watch` снова срабатывает.** Парсер записи трассы требовал `"args"` в
60 символах от `"hook"`, а реальная запись занимает 63–67 (tid, tick, ret):
первая же запись отбрасывалась, до таймаута печатался пустой результат, и
git-конвейер не запускался никогда. Заголовок записи пропускается
структурно, счётчики записи — 64-битные.

**Таймаут рукопожатия больше не занимает цель навсегда.** Если payload
стартовал дольше таймаута хоста (медленный антивирус на копии DLL), поздний
ответ укладывал его спать с занятым блоком — каждая следующая сессия к этой
1С отказывала до перезапуска. Хост паркует блок в «exit»: поздний payload
уходит сам и блок освобождается; ответ handshake публикуется только в
ждущий блок и не затирает ни «exit» сторожа, ни отравление.

**Поздний ответ не ложится поверх нового запроса.** Проверка номера запроса
в публикации ответа стояла до копирования буфера: между проверкой и
публикацией хост успевал забрать слово и положить следующий запрос — старый
ответ публиковался поверх, новый терялся с вводящим в заблуждение текстом.
Номер перечитывается непосредственно перед публикацией.

**`IsReadable` не врёт у вершины адресного пространства.** Адрес рядом с
потолком плюс длина заворачивали диапазон: страж отвечал «читаемо», и
следующее чтение падало внутри 1С. Сравнение переведено на вычитание.

**Сканеры считают по документированным дефолтам.** Общий парсер
предзаполнял `--count` значением 64, и собственные дефолты команд
(`heapobjects` — 20000, `memmap` — 60, `findvalue` — 32, `byhwnd` — 16) не
работали никогда: `heapobjects` без `--count` собирал 64 объекта и строил
статистику классов по первым попавшимся. Дефолты стали живыми, `--count 0`
— отказом вместо молчаливой подмены.

**`exports` и `imports` с длинными именами остаются валидным JSON.**
Элемент собирался в буфер 512 байт: манглированное имя длиннее ~440 символов
резалось посреди JSON-строки при `status:ok` (тот же класс дефекта, что
раньше закрыли для `pe`). Элемент собирается строкой без фиксированного
буфера.

**Нативное меню и цепочка команд: пять правок.** Приёмник меню на x64 берёт
оффсет, найденный дискавери, а не жёсткий 0x20 (на сборке с другим оффсетом
`cmd` работал, меню — молча нет). Каждый `cmd` больше не обходит всю память
процесса: кадр из дискавери переиспользуется после перевалидации. Захват
приёмника по событию проверяет калиброванный vtable кадра и слота до вызова
платформенного кода — чужой объект больше не исполняет мусор и не сбрасывает
живой захват. После сбойной команды восстанавливается только рамка, которой
адресовался маршал: легитимная модальность параллельного диалога больше не
ломается чужим отказом. Быстрый путь маршала проверяет класс окна:
переиспользованный HWND чужого класса не даёт вечного «UI thread did not
answer».

**8.5: сбойная команда больше не оставляет Конфигуратор без ввода.**
Восстановление отключённой рамки после transmit-исключения работало только
на 8.3-пути — на 8.5 рамка оставалась выключенной. Вызывается и там.

**GitBar: три правки.** Списки запрашивают длину элемента перед чтением —
путь глубокой выгрузки, subject стэша или аннотация тега длиннее 1023
символов больше не читаются за стек. Нативное меню показывает панель без
единого ожидания на UI-потоке 1С: до 5.5 секунд заморозки Конфигуратора
внутри transmit больше нет, запрошенное действие уезжает в поток бара.
«Переключить» на ветке `remotes/…` отказывает с подсказкой
`git checkout -b <имя> <ветка>` — молчаливый detached HEAD невозможен, а
успешное переключение показывает вывод git.

**Хосты: четыре правки.** Таблица решения инъекции отличает хэндл модуля от
кода аварии: NTSTATUS удалённого потока (0xC0000005 и соседи) больше не
печатается как «injected ok» по умершей цели. Фолбэк лога payload пишет в
буфер ограниченно: длинный TEMP больше не переполняет стек на потоке 1С.
GUI держит `cmd`/`cmd85`/`xref` 120 секунд, как CLI: выгрузка из командной
строки GUI перестала сообщать «(нет ответа)» при работающем в 1С диалоге.
Агент восстанавливает иконку трея после перезапуска explorer — агент больше
не теряет управление без выхода из процесса.

- Release-сборки x64 и x86 (`/W4 /WX`) — без предупреждений; CTest 4/4 на
  каждой разрядности (`cli_help`, `unit`, `hook_smoke`, `hook_stress`);
  `unit` — 172 теста / 1502 проверки на x64, 169 / 1461 на x86 (было

  отказ oversized-ответа вместо обрезки; `--count 0` и живой дефолт
  `heapobjects` (старый код отвечал потолком 64); парсер записи трассы на

  затрагивается); NTSTATUS в таблице решения инъекции.

## Установка

`v8inject-v0.8.2-x64.zip` / `v8inject-v0.8.2-x86.zip` — `v8inject.exe`,
`v8inject-gui.exe`, `v8inject-agent.exe`, `v8i_payload.dll` плюс тексты
лицензий. Распакуйте архив той же разрядности, что ваша платформа 1С, и
запускайте `v8inject.exe`, `v8inject-gui.exe` или `v8inject-agent.exe` из
каталога с `v8i_payload.dll`. Нативный пункт меню включён по умолчанию
(на 8.3.27.2342 x64); ключ `[git] nativemenu=0` в
`%APPDATA%\v8inject\gitbar.ini` возвращает оверлей-реплику.
