# Живая проверка после разбора 2026-11-12

Что именно изменилось в v0.2.20 и как это проверить на настоящей платформе.
План рассчитан на один рабочий день; пункты A обязательны, B — если вы
пользуетесь соответствующей возможностью, C — если у вас есть 8.5.

Автоматическая часть (запуск 1С, внедрение, проверка окна панели) уже есть:
`tools/check_gitbar.sh [8.3|8.5] [--keep]`.

---

## 0. Подготовка

1. Собрать свежее (или взять zip из релиза v0.2.20):

   ```bat
   cmake --build build\x64 --config Release
   cmake --build build\x86 --config Release
   ```

2. Положить рядом с `v8inject.exe` нужный `v8i_payload.dll` **той же
   разрядности**, что и целевой 1С: x86-конфигуратор → `build\x86\bin\x86`,
   x64 → `build\x64\bin\x64`.

3. Сделать копию рабочей копии git, которую будет видно панель:

   ```bat
   git status
   xcopy E:\dump\config E:\dump\config.bak /E /I
   ```

   Панель работает с тем репозиторием, на который указывает `dumpdir` в
   `%APPDATA%\v8inject\gitbar.ini`. Все пункты B2–B4 (отмена правок, удаление
   ветки/stash/тега) — необратимые операции, поэтому проверять их надо на
   отдельной ветке или на копии.

4. Закрыть лишние экземпляры 1С (в тестах используется `--pid`, чтобы не
   попасть не в тот процесс).

5. Знать, где искать логи:

   | Что | Где |
   |---|---|
   | лог хоста и payload | `<папка v8inject.exe>\v8inject.log` |
   | дамп классов окон (CBT) | `<папка v8inject.exe>\v8inject.log.cbt.txt` |
   | настройки панели | `%APPDATA%\v8inject\gitbar.ini` |

   Лог пишется и хостом, и payload'ом в один файл — по префиксу `[pid …]`
   видно, кто пишет.

## A. Обязательно: инъекция и связь

- [ ] **A1. Инъекция и handshake.**

```bat
v8inject inject 1cv8.exe --dll build\x64\bin\x64\v8i_payload.dll
v8inject probe 1cv8.exe
```

Ожидание: `{"status":"ok",...}` от `probe`, в логе — `command received: probe`.

- [ ] **A2. Повторная инъекция не ложно-успешна.** Изменение в `injector.cpp`
касается трактовки таймаута: раньше зависшая загрузка payload'а выглядела как
успех. Проверить, что обычная инъекция по-прежнему сообщает об успехе, а
негативный случай — на живом 1С воспроизвести трудно, достаточно убедиться,
что `inject` завершается кодом 0 и в логе нет `RemoteLoadLibrary → FAILED`.

- [ ] **A3. Разрядность цели.** В GUI (или `v8inject modules 1cv8.exe`) проверить,
что для x86-конфигуратора выбирается x86-payload, а для x64 — x64. Раньше на
32-битном хосте все процессы считались 64-битными.

```bat
v8inject modules 1cv8.exe
```

Ожидание: в списке у процесса 1С верная разрядность; если открыт x86-1С на
x64-Windows — `is64=false`.

- [ ] **A4. GitBar появляется и живёт.**

```bat
v8inject gitbar 1cv8.exe
```

Ожидание: панель справа в ряду тулбара, 12 кнопок; ответ
`{"status":"ok","visible":true}`. Через минуту панель должна по-прежнему
отвечать (перерисоваться при наведении) — это базовая проверка на зависание.

- [ ] **A5. Скрытие и повторный показ.**

```bat
v8inject gitbar hide 1cv8.exe
v8inject gitbar 1cv8.exe
```

Ожидание: панель исчезает и появляется снова без перезапуска 1С.

## B. GitBar (обязательно, если работаете с панелью)

- [ ] **B1. Меню действий.** Многоточие в конце ленты → меню в стиле 1С: фон
`#F8F7EE`, бежевая полоса слева, иконки, золотая колонка git-команд справа.
Пункт «Настройки…» открывает диалог.

- [ ] **B2. Настройки сохраняются — ключевой пункт.**

1. Закройте 1С. Удалите папку `%APPDATA%\v8inject` целиком.
2. Запустите 1С, откройте настройки панели, поменяйте `dumpdir` (или любой
   путь), нажмите «ОК».
3. Ожидание: папка `%APPDATA%\v8inject` появилась, файл `gitbar.ini` создан,
   **окно с ошибкой не показано**.
4. Откройте настройки заново → значения на месте.
5. Если файл создать не удалось (нет прав на профиль) — должно появиться
   понятное сообщение «Не удалось записать настройки», а не тишина.

- [ ] **B3. Кириллица в рабочей копии.**

1. В папке выгрузки создайте файл с кириллическим именем, например
   `Отчёт по продажам.txt`, и внесите в него правку.
2. Панель → «Рабочая копия…».
3. Ожидание: имя файла читается нормально, а не как `\320\237.txt`.
4. Нажмите «Индексировать» → файл должен попасть в индекс (это и есть
   проверка: раньше `git add` получал экранированный путь и падал).
5. Проверка из консоли: `git status` в папке выгрузки показывает файл в
   индексе.

- [ ] **B4. Подтверждения необратимых операций.**

1. «Рабочая копия…» → выберите изменённый файл → «Отменить».
   Ожидание: диалог «Действие необратимо…» с Да/Нет. Выберите **Нет** →
   правки в файле должны остаться.
2. Снова «Отменить» → **Да** → правки пропадают (это ожидаемо; делайте на
   копии из п.0.3).
3. Создайте ветку `test-confirm` → «Ветки…» → «Удалить» → должен появиться
   диалог. Аналогично для тега (`test-confirm`) и stash.

- [ ] **B5. Панель не зависает на git, ждущем ввод — ключевой пункт.**

Это проверка исправления чтения из трубы: раньше панель могла встать
намертво.

1. В `gitbar.ini` укажите `remote` = адрес приватного репозитория по HTTPS,
   где нет сохранённых учётных данных (или удалите их из диспетчера
   учётных данных Windows для этого хоста).
2. Нажмите «Пуш в удалённый репозиторий».
3. Ожидание: git спросит логин/пароль в тултипе панели; панель при этом
   **остаётся живой** — наводите курсор на кнопки, они подсвечиваются.
4. Через 120 с (таймаут) операция прерывается, в тултипе — `<timeout>`,
   панель продолжает работать.
5. Если панель перестала реагировать на наведение — это откат исправления
   B5 (см. раздел «Откат»).

- [ ] **B6. История коммитов.** «История коммитов» → окно в палитре 1С: бежевый
хром, белые строки, голубое выделение, граф веток, ржавые подписи колонок.
Выберите коммит → дифф справа. Кликните по файлу в диффе — патч должен
перерисоваться.

- [ ] **B7. Списки.** «Ветки…», «Stash…», «Теги…», «Рабочая копия…» — списки
заполняются, кириллица в именах веток и тегов читается.

## C. Хуки (высокий риск — проверять в первую очередь после GitBar)

Изменение в `hook.cpp` затрагивает перенос RIP-относительных операндов: при
разрядке ветки `rel8 → rel32` операнд раньше вставал на несколько байт мимо
адреса. Ошибка здесь = чтение/запись по чужому адресу внутри 1С.

- [ ] **C1. Установка и снятие хука.**

```bat
v8inject hook 1cv8.exe core83.dll!findMethod --name test
v8inject hooks 1cv8.exe
v8inject trace 1cv8.exe --count 5
v8inject unhook 1cv8.exe all
```

Ожидание: `{"status":"ok","id":N}`; в `hooks` хук виден с числом вызовов;
в `trace` — записи с аргументами; `unhook all` возвращает `removed:N`.

- [ ] **C2. Живость цели после хука.** После установки хука позапустите в 1С
действие, которое вызывает хукнутую функцию (например, открытие формы),
и убедитесь, что 1С не упала и ведёт себя как обычно. Это главный признак
того, что трамплин собран верно.

- [ ] **C3. Возврат байтов.** После `unhook` функция должна работать как обычно;
в логе — `hook N removed`.

- [ ] **C4. `cmd` после хука.** Хук на `findMethod` и вызов команды `cmd` — вместе
не должны мешать друг другу.

## D. Команды CLI (новые в v0.2.20)

Раньше эти команды понимал payload, но не понимал CLI.

- [ ] **D1. `cmd 45`** — открывает в 1С модальное окно выгрузки; **ответ
  придёт после того, как вы закроете это окно** (у команды увеличенный
  таймаут 120 с). Отмена диалога безопасна.
- [ ] **D2. `cmdinfo`** — читает, как на этой платформе ищется приёмник
  команд.
- [ ] **D3. `menu`** — список пунктов меню процесса (только чтение).
- [ ] **D4. `menucmd`** — вызов пункта меню по id: подставьте id из вывода
  `menu` и выберите безобидный пункт (например, «О программе»).

```bat
v8inject cmd 1cv8.exe 45      :: выгрузка конфигурации в файлы (откроется диалог 1С)
v8inject cmdinfo 1cv8.exe     :: как на этой платформе ищется приёмник команд
v8inject menu 1cv8.exe        :: список пунктов меню процесса
v8inject menucmd 1cv8.exe <hwnd> <id>   :: вызов пункта меню по id
v8inject cmd85 1cv8.exe 45    :: то же для 8.5
v8inject frames 1cv8.exe      :: что прислал eventCreateFrame (только 8.5)
```

## E. 8.5 (если есть платформа)

- [ ] **E1. `cmdinfo` и `frames`** — читают цепочку приёмника и дамп события.
- [ ] **E2. `cmd85 45`** — открывает окно выгрузки на 8.5.

```bat
v8inject cmdinfo 1cv8.exe
v8inject frames 1cv8.exe
v8inject cmd85 1cv8.exe 45
```

Ожидание: `cmdinfo` показывает найденную цепочку приёмника; `frames` — дамп
события; `cmd85 45` открывает окно выгрузки.

Отдельно: ранняя подписка через WH_CBT работает через поток-наблюдатель —
он не менялся. Хук на `CreateWindowExW` **остаётся выключенным** (см.
`docs/AUDIT.md`, A15): трамплин переписан на движковый, но путь на живой
платформе не проверен, включать его пока не нужно.

## F. Если что-то сломалось

| Симптом | Где искать | Что делать |
|---|---|---|
| Панель не появляется | `v8inject.log`: строки `RemoteLoadLibrary`, `handshake` | Проверьте разрядность payload'а и путь к DLL |
| Панель не отвечает | лог: последняя строка от payload'а | Проверьте B5 — вероятен зависший git; закройте 1С, перезапустите |
| `git add` на кириллическом файле падает | лог: вывод git | Проверьте, что `%APPDATA%\v8inject\gitbar.ini` не переопределяет `core.quotepath` |
| Настройки не сохраняются | лог: `cannot write ini key` | Проверьте права на `%APPDATA%` |
| 1С упала после установки хука | `v8inject.log`: `hit id=…`, `frames:` | Хук снимается: `v8inject unhook 1cv8.exe all`; затем `git log`/`git diff` для анализа |
| `cmd 45` не отвечает | лог: `cmd: invoking designer command` | Диалог выгрузки всё ещё открыт в 1С — закройте его |
| `probe` не отвечает | лог: `command received:` | Проверьте, что в 1С открыта конфигурация (payload работает в режиме конфигуратора) |

## Откат

Всё возвращается одним движением:

```bat
git checkout 4254e51        :: состояние до разбора (v0.2.19)
cmake --build build\x64 --config Release
```

Или откат только одного узкого места — например, если сомневаетесь в
изменении хуков, верните `src/payload/hook.cpp` из коммита `be4ecd1^`:

```bat
git checkout be4ecd1^ -- src/payload/hook.cpp
```

Если 1С падает — закройте её **без сохранения** и не запускайте конфигуратор
на рабочей базе, пока причина не найдена: изменения в хуках затрагивают
память процесса.
