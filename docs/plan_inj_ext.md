# План исследования оконной системы 1С 8.5.1 — расширенная редакция

**Проект:** v8inject — инжектор и точка расширения для процессов 1С:Предприятие
**Репозиторий:** https://github.com/fishca/v8inject
**Цель:** повторить функционал Снегопата — управление произвольными командами и
окнами Конфигуратора, массовое редактирование метаданных
**Целевая платформа:** 1С:Предприятие 8.5.1, Конфигуратор (x64)
**Кому адресован документ:** разработчику уровня «джун», который впервые берётся
за реверс платформы. Все шаги расписаны так, чтобы их можно было выполнять
последовательно, не додумывая.

---

## 0. Как читать этот документ

Документ состоит из трёх частей:

1. **Общие правила** (§1) — читать целиком до начала работы, это инварианты,
   нарушение которых роняет 1С и съедает день отладки.
2. **Фазы 0–5** (§2–§7) — по одной фазе за раз. Каждая фаза имеет одинаковую
   структуру:
   - **Зачем** — что даёт фаза и что будет невозможно без неё;
   - **Предусловия** — что должно быть сделано/установлено;
   - **Шаги** — пронумерованные действия с точными командами;
   - **Файлы** — что создаём/меняем в репозитории;
   - **Проверка** — как убедиться, что шаг выполнен (без «кажется, работает»);
   - **Грабли** — что обычно ломается и как это распознать;
   - **Готово, когда** — критерий приёмки фазы.
3. **Предложения по доработкам** (§8) — то, чего в исходном плане нет, но что
   сильно сократит сроки или снизит риск. Помечено приоритетом `P0/P1/P2`.

Правило работы: **не начинать следующую фазу, пока не закрыта предыдущая.**
Исключение — Фазы 1 и 2: их можно вести параллельно (см. §2.0 и §4.0).

### 1.5 Инварианты (нарушение = падение 1С)

1. **Любой вызов внутренних функций ядра — только на UI-потоке 1С.** Механизм
   готов: временный subclass главного окна + синхронное `WM_APP+0x602`
   (`V8iSubclass85` / `V8iStartStartupWatch` в `src/payload/v8i_export.cpp`).
   С чужого потока — `0xC0000005`.
2. **Каждая payload-команда — под SEH.** Падение должно возвращать JSON-ошибку,
   а не убивать Конфигуратор.
3. **`__try` несовместим с объектами C++ в том же кадре** (MSVC `C2712`).
   Внутри `__try` — только POD: массивы, `uintptr_t`, `char[]`. Результат
   конвертируется в `std::string` снаружи.
4. **Скан памяти — постранично (4 КБ).** Одна невалидная страница не должна
   обрывать весь регион; при `ReadProcessMemory == false` — `continue`, не `break`.
5. **Эвристика vtable:** минимум 3 из первых 4 указателей должны попадать внутрь
   исполняемого модуля, иначе это ASCII-данные, а не vtable.
6. **Экспорты читать с диска.** В памяти 8.5 зануляет export directory
   `core85.dll` и подменяет PE-Magic. Готовый код —
   `V8iResolveExportFromFile` в `src/payload/v8i_export.cpp`.
7. **Никаких хардкодов RVA.** Только runtime-резолв по экспортам/паттернам либо
   таблица билда в `data/builds/<version>.json` (см. §8, P0-3).
8. **Лог — рядом с exe** (`%APPDATA%\v8inject\agent.log`), не в `%TEMP%`.
9. **Одна команда = один измеримый результат.** Никаких «поковырялись»: каждая
   фаза закрывается артефактом (файл, JSON, команда, проходящая проверку).

### 1.6 Инструменты, которые уже есть

### 2.2 Шаги

**Шаг 0.2.3. Реализовать `exports85`.**

Сейчас `V8iResolveExportFromFile` умеет искать **один** экспорт по префиксу
имени. Нужно расширить до перечисления всех.

Что сделать в `src/payload/v8i_export.cpp`:

1. Рядом с `V8iResolveExportFromFile` добавить структуру:

   ```cpp
   struct V8iExportEntry {
       char name[256];
       uint32_t ordinal;
       uint32_t rva;
   };
   ```

2. Написать `int V8iDumpExportsFromFile(const wchar_t* modulePath,
   V8iExportEntry* out, int maxEntries)` — разбор PE с диска:
   - открыть файл `CreateFileW`, прочитать заголовки (`IMAGE_DOS_HEADER` →
     `IMAGE_NT_HEADERS`), проверить `SizeOfOptionalHeader`, магию (`0x20B` —
     PE32+, `0x10B` — PE32);
   - DataDirectory экспортов: `opt + (magic == 0x20B ? 112 : 96)`;
   - пройти `IMAGE_EXPORT_DIRECTORY`: `NumberOfNames`, массивы `AddressOfNames`
     (RVA → файловое смещение через таблицу секций), `AddressOfNameOrdinals`,
     `AddressOfFunctions`;
   - имя = строка по RVA из `AddressOfNames`, RVA функции =
     `AddressOfFunctions[ordinal]`.

3. Зарегистрировать команду `exports85 <модуль> [--count N]` рядом с
   `cmdinfo` (см. `CmdInfoToJsonA` как образец регистрации и формат ответа).

Формат ответа (JSON, одна строка):

```json
{"status":"ok","module":"core85.dll","count":1234,"exports":[
  {"name":"?current_process@core@@YAPEAVSCOM_Process@1@XZ","ordinal":17,"rva":"0x2EB2A0","va":"0x7FFA...","section":".text"}
]}
```

`section` — имя секции, в которой лежит RVA (полезно: `.text` — код,
`.rdata` — данные).

### 2.5 Грабли

| Симптом | Причина | Лечение |
|---|---|---|
| `count: 0` | читаем из памяти, а не с диска | путь брать из `GetModuleFileNameExW`, читать файл |
| мусор в именах | неверное `opt`/`DataDirectory` | `opt = nt + 20`, DD = `opt + 112` для PE32+ |
| смещения «плывут» | RVA не переведён в файловое смещение | использовать таблицу секций (`VirtualAddress`/`PointerToRawData`) |
| пустые имена | `memcmp` на NUL-терминированной строке | сравнивать длину без NUL (`strlen`, не `sizeof`) |

## 3. Фаза 1. Якорь на объектную модель

**Срок:** 2–3 дня. **Риск:** средний. **Новые команды:** `frames`, `svcscan`.

### 3.0 Зачем

Нужен **один** надёжный способ получить `this` главного фрейма (`ITopLevelFrame`).
Пока его нет, команды и окна трогать нельзя. Сейчас три недоведённых пути —
задача фазы: свести к одному работающему.

### 3.1 Предусловия

- Фаза 0 закрыта (есть таблица экспортов);
- прочитан §1.5, особенно п.1 (UI-поток) и п.2 (SEH).

### 3.2 Шаги

**Шаг 1.2.1. `eventCreateFrame` end-to-end (команда `frames`).**

Что уже есть: подписка (`IEventService::_subscribe`, слот 4) работает,
`notify` (слот 3) проверен самопроверкой — наш `onEvent` вызывается.

Чего нет: в `onEvent` не сохраняется объект.

Что сделать:

1. В `IEventRecipient::OnEvent(const GUID& id, intptr_t val, IUnknown* obj)`
   сохранить:
   - `obj` (указатель);
   - vtable: `*(uintptr_t*)obj`;
   - первые 64 байта: `memcpy` под `IsReadable(obj, 64)`;
   - модуль и RVA vtable (`modRva`).
2. Накопить до 32 записей в POD-массиве (без `std::vector` внутри `__try`).
3. Отдавать JSON командой `frames`:

```json
{"status":"ok","frames":[
  {"ptr":"0x1A2B...","vtable":"0x7FFA...","module":"frame.dll","rva":"0xC9B988",
   "dump":"48 8B 01 48 85 C0 ..."}
]}
```

**Как проверить, что событие вообще приходит:** подписка должна быть выполнена
**до** создания главного окна. Наш опыт: подписка после старта — событие уже
прошло (`evFrame=0`). Варианты ранней подписки — §8, P0-1 (`WH_CBT`) и P0-2
(движок Снегопата).

**Шаг 1.2.2. `svcscan` — перебор сервисов процесса.**

Известно: `getService` — слот 14 vtable `SCOM_Process`
(`core85+0x418838`), и он отдаёт `IEventService` (`core85+0x3D6298`) и
`ICommandService` (`frame.dll+0xC9B988`).

Что сделать:

1. Получить `SCOM_Process*` на UI-потоке (механизм готов: `V8iCurProcFn` +
   `WM_APP+0x602`).
2. Для набора IID (из 8.3 и из `v8snapi`) вызвать слот 14 и записать
   `{iid, result, vtable}`. IID брать из `v8snack/snegopat-client/x64/modules/
   snegopat/v8api/*.v` — там готовые GUID и раскладка слотов (см. §8, P0-1).
3. Отдавать JSON командой `svcscan`.

**Грабля:** не перебирать слоты «в лоб» — на 8.5 слот 13 vtable процесса это
сеттер структуры, вызов портит объект и роняет 1С. Только известные слоты и
только с валидными IID.

**Шаг 1.2.3. Путь через окно (inline-хук).**

Заготовка есть (`V8iInstallCreateWindowHook`, коммит `cc7eed2`), отключена.

Порядок:

1. Включить хук, поставить лог на вход в detour: писать `hwnd`, `cls`,
   `lpParam` (для `CreateWindowExW` это 13-й аргумент).
2. Запустить 1С, открыть базу, посмотреть лог: приходит ли в `lpParam`
   указатель на объект 1С.
3. **Если приходит** — это самый дешёвый якорь: сохранить, проверить vtable
   (должна быть в `.rdata` модуля `frame.dll`/`config.dll`).

**Найденные ограничения (проверено живьём, не повторять ошибку):**

- `user32!CreateWindowExW` для окон 1С **не вызывается** (`cwHits=0`);
- `wbase85!V8CreateWindowEx` тоже не вызывается;
- окно создаётся через `win32u!NtUserCreateWindowEx` (пролог
  `4C 8B D1 B8 6F 10 00 00 …`, 16 целых байт), но при инжекте после старта
  `cwHits=0` — окно уже создано;
- подписка **внутри** detour роняет 1С: в момент создания окна ядро ещё не
  готово (`0xC000041D` — исключение в callback).

**Вывод:** inline-хук окна годится только при инжекте **до** создания окна, а
такой инжект на 8.5 не работает (payload не обслуживает сессию в стартующем
процессе). Поэтому основной путь — §8 P0-1/P0-2.

### 3.3 Файлы

- `src/payload/v8i_export.cpp` — `frames`, `svcscan`, поля накопления фреймов;
- `docs/RECON-85.md` — раздел «Якорь: рабочая цепочка».

### 3.4 Проверка

- `frames` отдаёт ≥1 запись с vtable внутри `frame.dll`/`config.dll`;
- `svcscan` отдаёт `IEventService` и `ICommandService` с ожидаемыми vtable
  (`core85+0x3D6298`, `frame.dll+0xC9B988`);
- после перезапуска 1С результат воспроизводится (не «случайно сработало»).

### 3.5 Грабли

| Симптом | Причина | Лечение |
|---|---|---|
| `evFrame=0`, `evCount` растёт | подписка после создания окна | ранняя подписка (§8 P0-1/P0-2) |
| `0xC000041D` | исключение внутри callback | не вызывать ядро из хука окна |
| `0xC0000005` на `current_process` | вызов не с UI-потока | `WM_APP+0x602` |
| объект «портится» | перебор слотов vtable | только известные слоты + валидные IID |

### 3.6 Готово, когда

Есть документированная цепочка «от запуска 1С до указателя на
`ITopLevelFrame`», воспроизводимая после перезапуска, и команда, которая её
отдаёт.

## 4. Фаза 2. Реестр команд

**Срок:** 3–4 дня. **Риск:** низкий. **Новые команды:** `cmdrecord`, `cmdlist`.

### 4.0 Зачем и почему можно параллельно

Команда 1С — пара `{GUID группы, номер}`. Без реестра управлять нечем.
Реестр собирается **перехватом** вызовов, поэтому не требует готового якоря из
Фазы 1 — фазы можно вести параллельно.

### 4.1 Предусловия

- `hook.cpp` работает (есть тест `v8i_hook_target.exe`);
- умеем ставить inline-хук и снимать его (см. `HookRemoveAll`).

### 4.2 Шаги

**Шаг 2.2.1. Найти `transmitCommand` в 8.5.**

`ITopLevelFrame::commandReceiver(out ICommandReceiver)` — метод фрейма; у
`ICommandReceiver` есть `transmitCommand`. Раскладка слотов — в
`v8snack/snegopat-client/x64/modules/snegopat/v8api/window.v` (см. §8 P0-1).

Действия:

1. Открыть `v8api/window.v`, найти `:iface ICommandReceiver` и номер слота
   `transmitCommand`.
2. Найти адрес функции: от vtable `ICommandReceiver` (получается из
   `getService(IID_ICommandService)` → `commandReceiver`) взять слот.
3. Записать `module+RVA` в `docs/RECON-85.md`.

**Шаг 2.2.2. Реализовать `cmdrecord start|stop|dump`.**

1. Inline-хук на найденный адрес (`hook.cpp`): сохранить регистры, вызвать
   оригинал, залогировать аргументы.
2. Лог — массив POD-записей:

   ```cpp
   struct CmdRec { uintptr_t group; int num; uintptr_t param; uintptr_t object; DWORD tick; };
   ```

   `group` — указатель на GUID (скопировать 16 байт), `num` — номер команды,
   `param` — параметр, `object` — объект.
3. `dump` — JSON:

   ```json
   {"status":"ok","records":[
     {"group":"{F10CBB81-...}","num":45,"param":"","object":"0x0","ts":123456}
   ]}
   ```

4. Запись **не должна** тормозить UI: буфер фиксированного размера (например,
   4096 записей), при переполнении — счётчик потерь.

**Шаг 2.2.3. Ручной проход по меню.**

1. `cmdrecord start`.
2. Пройти вручную: Файл → все пункты; Правка; Конфигурация; Отладка; Окна;
   Сервис. После каждого пункта — пометка в блокноте, что нажимали.
3. `cmdrecord stop`, `cmdrecord dump` → JSON.
4. Сопоставить: `{группа, номер}` ↔ пункт меню. Результат — в
   `docs/COMMANDS.md` (таблица: пункт, группа, номер, параметр).

**Шаг 2.2.4. `cmdlist [--group <guid>]`.**

Отдаёт накопленный реестр (из `cmdrecord`) в читаемом виде. Фильтр по группе.

**Шаг 2.2.5. Проверить источник «строки в `.rdata`».**

В 8.3 рядом с командами лежали строки (`"FileOpen"`, `"ConfigOpen"`). На 8.5
проверить: `findvalue "ConfigOpen"` → `xref` → рядом структура команды. Если
сработает — получим имена без ручного прохода.

### 4.3 Файлы

- `src/payload/hook.cpp` / новый `src/payload/cmdrecord.cpp` — хук и буфер;
- `src/payload/v8i_export.cpp` — команды `cmdrecord`, `cmdlist`;
- `docs/COMMANDS.md` — таблица команд (генерируется из `cmdrecord dump`).

### 4.4 Проверка

- `cmdrecord dump` после ручного прохода содержит ≥20 записей;
- контрольная точка: команда «выгрузить конфигурацию в файлы» присутствует и
  её номер совпадает с тем, что реально срабатывает (проверить вызовом);
- `cmdlist` фильтрует по группе.

### 4.5 Грабли

| Симптом | Причина | Лечение |
|---|---|---|
| хук не срабатывает | функция вызывается через vtable с другим адресом | хук на конкретный слот vtable, не на «похожую» функцию |
| 1С падает при хуке | испорчены регистры/стек | сохранять все volatile-регистры, выравнивать стек |
| записи пустые | `group` — не указатель, а значение | проверить разыменование на 2-3 вызовах вручную |
| буфер переполняется | слишком много событий | кольцевой буфер + счётчик потерь |

### 4.6 Готово, когда

Есть `docs/COMMANDS.md` с полным списком пунктов меню Конфигуратора 8.5 и их
`{группа, номер}`, полученным через `cmdrecord`, и команда `cmdlist`.

## 5. Фаза 3. Оконная система

**Срок:** 4–5 дней. **Риск:** средний. **Новые команды:** `wndclass`, `wintree`.

### 5.1 Зачем

Чтобы управлять окнами (открывать, закрывать, читать состояние), нужно понимать
их модель: классы, WndProc, иерархию, связь Win32-окна с объектом 1С.

### 5.2 Шаги

**Шаг 3.2.1. `wndclass <имя>`.**

1. Взять `GetClassInfoExW` для класса (`V8TopLevelFrame`, `V8Window`,
   `V8ToolTipWindow`, `V8CloseAllButton`, `V8ValidationMessageWnd`,
   `V8EMSGServer`).
2. Из `WNDCLASSEX.lpfnWndProc` получить адрес → `modRva` → `{модуль, RVA}`.
3. Отдавать `{class, wndproc, module, rva, style, hbrBackground}`.

**Шаг 3.2.2. Разобрать WndProc главного фрейма.**

1. Дизассемблировать WndProc (`disasm.cpp`, Capstone).
2. Найти сравнения с `WM_COMMAND` (0x0111) — switch/if-цепочку.
3. Восстановить: какие `wParam` (ID команд) обрабатываются и куда ведут.
4. **Проверить гипотезу:** послать `WM_COMMAND` с найденным ID и посмотреть,
   выполняется ли действие. Если да — управление командами возможно **без**
   вызова внутренних функций (самый безопасный путь).

**Грабля:** на 8.5 окна рисуются через DWM, дочерних Win32-окон у панелей нет —
`EnumChildWindows` ничего не даёт. Иерархия — в объектах 1С, не в Win32.

**Шаг 3.2.3. `wintree [--depth N]`.**

1. Корень — главное окно процесса (`EnumWindows` + фильтр по PID и классу).
2. Для каждого окна: `GetClassName`, `GetWindowRect`, `GetWindowLongPtr(
   GWLP_HWNDPARENT)`, поле `+0x34` объекта (если объект известен).
3. Дети — через `GWLP_HWNDPARENT` и (если найдено) через объектную модель.
4. Отдавать дерево JSON с отступом по глубине.

**Шаг 3.2.4. Свойства окон.**

Минимум: заголовок (`GetWindowText`), размер/позиция (`GetWindowRect`),
видимость (`IsWindowVisible`), активность (`GetForegroundWindow`).
Чтение — через Win32; запись — `SetWindowText`/`SetWindowPos` только для окон,
которые мы сами создали (GitBar), чужие окна не трогать без явной команды.

### 5.3 Файлы

- `src/payload/v8i_export.cpp` — `wndclass`, `wintree`;
- `docs/RECON-85.md` — раздел «Модель окон 8.5».

### 5.4 Проверка

- `wndclass V8TopLevelFrame` отдаёт WndProc внутри `frame.dll`;
- `wintree` показывает главное окно и известные классы;
- отправка `WM_COMMAND` с найденным ID выполняет ожидаемое действие (для 2–3
  команд).

### 5.5 Грабли

| Симптом | Причина | Лечение |
|---|---|---|
| `wndclass` не находит класс | класс зарегистрирован позже | вызывать после открытия базы |
| дерево пустое | DWM, нет дочерних окон | строить по объектам, не по Win32 |
| `WM_COMMAND` игнорируется | 1С обрабатывает команды не через окно | вернуться к `transmitCommand` |

### 5.6 Готово, когда

`wintree` стабильно отдаёт дерево окон с классами и объектами, а `wndclass`
даёт WndProc для всех известных классов.

## 8. Предложения по доработкам (сверх исходного плана)

Отсортировано по приоритету. `P0` — сильно сокращает срок или снимает риск,
`P1` — заметно помогает, `P2` — приятно иметь.

### P0-1. Использовать `v8api` из Снегопата вместо реверса интерфейсов

**Проблема:** в плане Фазы 1–3 предполагают заново выяснять раскладку слотов
интерфейсов (`ITopLevelFrame`, `ICommandReceiver`, `IEventService`).

**Предложение:** в репозитории `fishca/v8snack` уже лежит
`snegopat-client/x64/modules/snegopat/v8api/*.v` — описания интерфейсов
платформы с **точными номерами слотов** (`:virt` + `+N`), GUID и версионными
ветками (`#if ver ...`). Там же `engine/mainframe.as` — рабочий код получения
`ITopLevelFrame` через `eventCreateFrame`, и `engine/com_events.as` — подписка.

**Что сделать:** перенести нужные `.v` в `docs/v8api/` (или подключить как
submodule), читать слоты оттуда, а не реверсить. Экономия — дни.

### P0-2. Взять механизм ранней подписки из Снегопата (WH_CBT + движок)

**Проблема:** наш `eventCreateFrame` не ловит фрейм, потому что подписка идёт
после создания окна, а в момент создания окна ядро ещё не готово (наш
`0xC000041D`).

**Как делает Снегопат:** нативная `snegopat.dll` **WH_CBT-хуком** ловит создание
окна заставки («все DLL платформы загружены, основное окно ещё не создано») и
вызывает `run()`, который подписывается. Причём `getEventService()` в
Снегопате — это `currentProcess().getService(...)` **через движок
`core_as.dll`**, а не прямой вызов `core85`.

**Что сделать (два варианта):**

- **P0-2a (быстрый):** поставить `WH_CBT`-хук из нашего payload **до** создания
  окна. У нас не получилось, потому что инжект после старта; но если запускать
  1С через `v8inject launch` и ставить хук в `v8i_probe` **до** `RunPayload` —
  хук успевает (проверено: хук срабатывает; падает именно подписка, потому что
  ядро не готово). Значит, в хуке нужно не подписываться сразу, а **дождаться
  готовности ядра** (опрос `current_process` с SEH в цикле) и только потом
  подписаться.
- **P0-2b (надёжный):** использовать `core_as.dll` (движок Снегопата) как
  прослойку: он уже умеет безопасно вызывать ядро 1С на 8.5. Наш payload
  вызывает его API вместо прямых вызовов.

### P0-3. Таблица калибровки по билдам вместо хардкодов

**Проблема:** план запрещает хардкодить RVA, но при этом все находки — это RVA
конкретного билда.

**Предложение:** файл `data/builds/<FileVersion>.json`:

```json
{"build":"8.5.1.1529","modules":{"core85.dll":{"sha256":"...",
 "exports":{"?current_process@core@@...":"0x2EB2A0"},
 "vtable":{"SCOM_Process":"0x418838"}}}}
```

Payload при старте: определяет версию, ищет файл, берёт RVA; если файла нет —
runtime-резолв по экспортам и предупреждение в лог. Это одновременно и
«не хардкод» (данные, не код), и воспроизводимость.

### P0-4. Автотесты каждой фазы в стиле `check_gitbar.sh`

**Проблема:** в плане приёмка описана словами; проверять руками — долго и
неповторяемо.

**Предложение:** на каждую фазу — скрипт `tools/check_<фаза>.sh` по образцу
существующего `tools/check_gitbar.sh` (запуск 1С → инжект → команда → разбор
JSON → exit 0/1). Тогда регрессия после любой правки — одна команда. Это уже
доказало себя: `check_gitbar.sh` поймал падение из-за CBT-хука.

### P0-5. Дампы при падении (post-mortem)

**Проблема:** каждое падение 1С сейчас расследуется заново.

**Предложение:** в payload — `SetUnhandledExceptionFilter` +
`MiniDumpWriteDump` в `%APPDATA%\v8inject\crash-<pid>-<ts>.dmp`. Плюс запись в
лог последней выполненной команды и стадии (`stage=N`). Тогда разбор падения —
минуты, а не часы.

### P1-1. Не инжектить, а использовать штатный механизм аддинов

**Наблюдение:** Снегопат попадает в процесс через `inject.dll`, но дальше
работает как штатный аддин-слой с движком `core_as.dll` (компиляция
AngelScript, `v8api`, пакеты инициализации). Это легальнее и стабильнее, чем
наши прямые вызовы.

**Предложение:** для задач «управление командами/окнами/метаданными» оценить
вариант «расширять Снегопат» (v8snack), а v8inject оставить для GitBar и
инжекта. Возможно, это дешевле, чем повторять его функционал.

### P1-2. CI на GitHub Actions

**Проблема:** релизы собираются руками, x86 и x64 могут разъехаться.

**Предложение:** workflow `.github/workflows/build.yml`: Windows-runner,
MSBuild x86+x64, `tools/check_*.sh` (где возможно без GUI — только сборка и
юнит-тесты), артефакты; релиз по тегу — автоматически (`gh release create`).
Часть GUI-проверок в CI не пойдёт (нужен рабочий стол) — их оставить локально.

### P1-3. Единый формат JSON-ответов и коды ошибок

**Предложение:** все команды payload отдают
`{"status":"ok"|"error","code":"...","message":"..."}`; коды — перечисление
(`E_NO_FRAME`, `E_UI_THREAD`, `E_SEH`, `E_GIT`...). Это упрощает автотесты и
разбор логов.

### P1-4. Таймауты и «стоп-кран» на каждую операцию

**Проблема:** вызов внутренней функции может подвесить UI 1С навсегда.

**Предложение:** каждая операция — с таймаутом (например, 5 с) и флагом
«прервано»; если команда не вернулась — писать в лог и возвращать ошибку, не
блокируя Конфигуратор. Плюс «стоп-кран» в агенте: одна кнопка «отключить
инжект/хуки» без перезапуска 1С.

### P1-5. Автоматический бэкап перед изменяющими операциями

**Предложение:** перед `UpdateDBCfg`, `LoadConfigFromFiles`, вызовами команд,
меняющих конфигурацию, — автоматическая выгрузка в файлы в
`backups/<ts>/`. Дёшево (уже умеем `DumpConfigToFiles`) и снимает страх
экспериментов.

### P2-1. Расширить `check_gitbar.sh` до полноценного smoke-теста

Добавить проверки: окно истории (`V8iGitLog`) открывается, список коммитов
непустой, дифф отрисован; окна «Рабочая копия»/«Ветки» открываются. Тогда
релиз сопровождается автоматическим подтверждением, что GitBar жив.

### P2-2. Документировать находки 8.5 в репозитории

Уже частично сделано в скилле; перенести в `docs/RECON-85.md` и
`docs/COMMANDS.md`, чтобы знания не жили только в чате/скилле.

### P2-3. Сравнение поведения 8.3/8.5 в одном прогоне

Скрипт `tools/check_both.sh`: прогон `cmdinfo` на 8.3 и 8.5, diff JSON —
сразу видно, что разъехалось между платформами.

```
    ▼                     │
Фаза 3 (окна)             │  → wintree
    │                     │
    ├── wndclass          │
    └── wintree           │
    ▼                     │
Фаза 4 (вызов) ◄──────────┘  → 4 контрольные команды
    │

```

Каждая стрелка — коммит с артефактом и обновлённым `docs/RECON-85.md`.

## 11. Глоссарий (для джуна)

| Термин | Что это |
|---|---|
| `ITopLevelFrame` | COM-интерфейс главного фрейма 1С; через него доступны команды |
| `ICommandReceiver` | интерфейс приёма команд; метод `transmitCommand(group, num, ...)` |
| `IEventService` | сервис событий; `subscribe(eventCreateFrame, recipient)` |
| `eventCreateFrame` | событие создания фрейма; GUID `{3573FFE0-2FFF-11D5-BF5E-0050BAE2BC79}` |
| `SCOM_Process` | объект процесса 1С; `getService(iid)` — слот 14 vtable |
| `transmitCommand` | вызов команды по паре `{GUID группы, номер}` |
| `WH_CBT` | Win32-хук создания окон; так Снегопат ловит заставку |
| `SEH` | структурированные исключения (`__try/__except`) — защита от падений |
| `vtable` | таблица виртуальных методов COM-объекта; лежит в `.rdata` |
| RVA | смещение от базы модуля (то, что не зависит от ASLR) |
