# Ревизия проекта v8inject — 2026-11-08

Полный осмотр репозитория: состояние, инвентарь, находки и рекомендации.
Каждая находка помечена приоритетом: **P0** — чинить сейчас, **P1** — в
ближайший спринт, **P2** — по возможности.

---

## 1. Что за проект и в каком он состоянии

Инжектор и точка расширения для процессов 1С:Предприятие (Конфигуратор).
Payload-DLL загружается в процесс 1С и обслуживает JSON-команды хостов через
разделяемую память: реверс-инструменты (дизассемблер, сканы памяти, хуки),
вызов штатных команд дизайнера и git-панель (GitBar).

Состояние: **активная разработка, две рабочие зоны**.

- Зона «8.3» стабильна: инжект, реверс-команды, хуки, GitBar (12 кнопок),
  вызов команд дизайнера `cmd` — работают на 8.3.27.1989 (x86 и x64).
- Зона «8.5» в разгаре (Фазы 0–1 плана [plan_inj_ext.md](plan_inj_ext.md)
  закрыты): ранняя подписка через WH_CBT работает, `cmd85` доводится до
  приёмки (receiver — слот 31).

Общее состояние репозитория: рабочее дерево чистое, `main` опережает
`origin/main` на 6 коммитов (находка A5).

## 3. Что хорошо (сильные стороны)

1. **Крайне дисциплинированная изоляция рисков в payload**: каждая команда под
   SEH, `__try` только с POD, лог одним `WriteFile` без CRT-буферизации,
   `SRWLOCK` вместо `std::mutex` (в чужом процессе может жить своя старая
   MSVCP140), никаких диалогов CRT в DllMain. Это правильный набор правил для
   кода, живущего в чужом процессе.
2. **Отказоустойчивый протокол**: CAS на отправке вместо блокировок, seqlock
   в кольцевом буфере трассы, `RemoteFree`-механики без гонок, диагностика по
   стадиям (kStage*).
3. **Тесты там, где можно автоматизировать**: hook_smoke покрывает все случаи
   релокации трамплина (ветки, tail-call, rel8→rel32) и гоняется в CI;
   `check_gitbar.sh` — честный E2E с живой платформой.
4. **Документация процесса реверса**: plan_inj_ext.md — образцовый документ
   (инварианты, фазы, грабли, критерии приёмки); RECON-85 фиксирует факты,
   а не «ощущения».
5. **Знания не теряются**: источники иконок (SOURCE.json), находки по
   Снегопату (шапки recon-скриптов), грабли прямо в комментариях кода.
6. **Hermetic-сборка**: Capstone вендорен осознанно (комментарий в
   cmake), CI собирает обе разрядности.

## 4. Находки

### A1 · P0 · README существенно устарел

- GitBar описан как «пять кнопок» — фактически **12** (pull/fetch/branches/
  stash/tags/status/история добавлены в коммитах `5a1221c…ae743f0`).
- «Совместимость: 8.3.x (проверялось на 8.3.24)» — проект сейчас
  целится в 8.5.1.1529 x64 и проверен на 8.3.27.1989.
- В «Структуре» нет `src/agent/` — компонент `v8inject-agent` существует с
  конца октября и в README не упомянут вообще, как и команды `watch`,
  `launch`, `hookcbt`, `cmdinfo`, `exports85`, `frames`, `cmd85`.
- «CI собирает на windows-latest» — workflow пинирует `windows-2022`.

→ README исправлен в этой ревизии; глубина уведена в docs/.

### A2 · P0 · `--help` не знает о половине команд

`PrintUsage` (`src/cli/main.cpp:15-54`) не перечисляет: `launch`, `hookcbt`,
`gitbar`, `cmdinfo`, `exports85`, `frames`, `cmd85`, `exports`, `scan`.
Команды при этом работают. Пользователь узнаёт о них только из README
(который сам отставал — A1).

### A3 · P0 · CLI больше не форвардит `cmd`, `menu`, `menucmd`, `str`

Payload-сторона жива (`wcsncmp(request, "cmd ", 4)` — `v8i_export.cpp:3510`,
`menu`/`menucmd`/`str` там же), но в CLI-диспетчере
(`src/cli/main.cpp:501-506`) этих имён нет: `v8inject cmd 1cv8.exe 2`
печатает usage и выходит с кодом 1. README до этой ревизии документировал
`cmd` как рабочую команду — регрессия прошла незаметно, потому что
рабочим путём стала сессия `attach`.

→ Либо добавить четыре имени в список форварда (2 строки), либо осознанно
документировать «только через attach» — но тогда убрать их из README-примеров.

### A4 · P0-закрыто · У вендоренного Capstone не было файла лицензии

`cmake/capstone.cmake:3` обещает «see LICENSE.TXT in the upstream tree», но
файла в `third_party/capstone/` не было — BSD-3-Clause требует сохранения
уведомления при редистрибуции.

→ Закрыто 2026-11-10: заведены `third_party/capstone/LICENSE.TXT` (3-clause
BSD, Copyright (c) 2013, COSEINC) и `third_party/capstone/LICENSE_LLVM.TXT`
(University of Illinois/NCSA — X86-дизассемблер LLVM-производный), в README
добавлена NOTICE-строка в раздел «Лицензия».

### A5 · P1 · 6 коммитов не опубликованы

Вся работа по 8.5 (ранняя подписка, cmd85, receiver-слот 31) существует
только локально. Опубликовать (`git push`) или хотя бы зафиксировать
намерение.

### A6 · P1 · Калибровочные константы в коде без таблицы билдов

`kFrameVtblRva = 0x2EFB50` (`v8i_export.cpp:3042`, комментарий
«8.3.27.1989 x64») и смещения x86-цепочки — константы конкретного билда прямо
в коде. Инвариант плана §1.5.7 («никаких хардкодов RVA») частично нарушен.
Предложение P0-3 (файл `data/builds/<version>.json` + загрузка в payload)
остаётся нереализованным. На 8.5 ситуация лучше (runtime-резолв), но
vtable-константы 8.5 (`config.dll+0x2ED3B0`) тоже живут в комментариях/коде.

### A7 · P1 · Единый формат JSON-ответов не введён

Предложение P1-3 плана (`{"status":..., "code":..., "message":...}` +
перечисление кодов) не реализовано: команды отдают разнородные формы.
Усложняет автотесты и разбор логов.

### A8 · P1 · Расхождение документации и кода: размер `Command`

`docs/RECON-85.md` §3.3: `Command` = 40 байт (CommandID с выравниванием 8).
Код: `V8Cmd` — 32 байта на x64 (`v8i_export.cpp:1104-1110`, комментарий
«16 + 4 + 4 + 8 = 32»). RECON — исследовательский документ; если кто-то будет
строить структуру по нему (Фаза 4), получится падение. Правку внести в
RECON-85 с пометкой о проверке живым вызовом.

### A9 · P2 · `SharedIo`: имя блока предсказуемо, `ERROR_ALREADY_EXISTS` не проверяется

`Client::Open` создаёт блок `Local\v8inject.<pid>`
(`src/host/client.cpp:59-61`) и не проверяет `GetLastError() ==
ERROR_ALREADY_EXISTS`. Любой процесс того же пользователя может создать блок
с таким именем раньше хоста; payload подключится к нему и будет исполнять
чужие команды. Атака локальная и малоправдоподобная, но закрытие дешёвое:
считать `ERROR_ALREADY_EXISTS` фатальной ошибкой Open.

### A10 · P2 · Мусор в локальном `build/*/bin` не покрыт `.gitignore`

Рядом с рабочими DLL лежат копии `v8i_payload.dll.old*` (более 10 штук).
Они не попадают в git (каталог build/ игнорируется целиком), но засоряют
каталог, откуда GUI подставляет payload по умолчанию, и однажды могут
уехать в артефакты CI (`path: build/*/bin/<arch>/*` загружает всё).
Почистить и не плодить `.old*` в bin.

### A11 · P2 · Покрытие тестами неравномерно

- Хуки — хорошо покрыты (hook_smoke, 4 сценария релокации).
- GitBar — E2E только локально (нужна 1С), в CI не идёт (осознанно).
- Цепочка `cmd`/`cmd85` (взаимодействие с 1С) — автотеста нет; это риск
  P0-4 плана: после каждой правки vtable-цепочки проверка ручная.
  Кандидат — `tools/check_cmd.sh` по образцу check_gitbar.sh.

### A12 · P2 · Прочее

- `docs/plan_inj_ext.md` §12 требует подписи коммитов `fishca <sergrud@mail.ru>`
  — в конфиге git указан только `fishca`; сверить `user.email`.
- `RECON-85.md` и `plan_inj_ext.md` пересекаются по теме слотов: после
  приёмки Фазы 1 стоит слить фактические находки в RECON-85 (план —
  исторический документ).
