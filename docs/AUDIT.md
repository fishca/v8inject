# Ревизия проекта v8inject — 2026-11-08

Полный осмотр репозитория: состояние, инвентарь, находки и рекомендации.
Каждая находка помечена приоритетом: **P0** — чинить сейчас, **P1** — в
ближайший спринт, **P2** — по возможности.

---

## 1. Что за проект и в каком он состоянии

Инжектор и точка расширения для процессов 1С:Предприятие (Конфигуратор).
Payload-DLL загружается в процесс 1С и обслуживает JSON-команды хостов через
разделяемую память: реверс-инструменты (дизассемблер, сканы памяти, хуки),
вызов штатных команд дизайнера и git-панель (GitBar).

Состояние: **активная разработка, две рабочие зоны**.

- Зона «8.3» стабильна: инжект, реверс-команды, хуки, GitBar (12 кнопок),
  вызов команд дизайнера `cmd` — работают на 8.3.27.1989 (x86 и x64).
- Зона «8.5» в разгаре (Фазы 0–1 плана [plan_inj_ext.md](plan_inj_ext.md)
  закрыты): ранняя подписка через WH_CBT работает, `cmd85` доводится до
  приёмки (receiver — слот 31).

Общее состояние репозитория: рабочее дерево чистое, `main` совпадает с
`origin/main` (находка A5 закрыта 2026-11-12).

## 3. Что хорошо (сильные стороны)

1. **Крайне дисциплинированная изоляция рисков в payload**: каждая команда под
   SEH, `__try` только с POD, лог одним `WriteFile` без CRT-буферизации,
   `SRWLOCK` вместо `std::mutex` (в чужом процессе может жить своя старая
   MSVCP140), никаких диалогов CRT в DllMain. Это правильный набор правил для
   кода, живущего в чужом процессе.
2. **Отказоустойчивый протокол**: CAS на отправке вместо блокировок, seqlock
   в кольцевом буфере трассы, `RemoteFree`-механики без гонок, диагностика по
   стадиям (kStage*).
3. **Тесты там, где можно автоматизировать**: hook_smoke покрывает ветки,
   tail-call и разрядку rel8→rel32, а rip-относительный операнд — юнит-стенд
   в `v8i_hook_target`/`unit_hook` (в smoke его не было, A75); и то и другое
   гоняется в CI; `check_gitbar.sh` — честный E2E с живой платформой.
4. **Документация процесса реверса**: plan_inj_ext.md — образцовый документ
   (инварианты, фазы, грабли, критерии приёмки); RECON-85 фиксирует факты,
   а не «ощущения».
5. **Знания не теряются**: источники иконок (SOURCE.json), находки по
   Снегопату (шапки recon-скриптов), грабли прямо в комментариях кода.
6. **Hermetic-сборка**: Capstone вендорен осознанно (комментарий в
   cmake), CI собирает обе разрядности.

## 4. Находки

### A1 · P0 · README существенно устарел

- GitBar описан как «пять кнопок» — фактически **12** (pull/fetch/branches/
  stash/tags/status/история добавлены в коммитах `5a1221c…ae743f0`).
- «Совместимость: 8.3.x (проверялось на 8.3.24)» — проект сейчас
  целится в 8.5.1.1529 x64 и проверен на 8.3.27.1989.
- В «Структуре» нет `src/agent/` — компонент `v8inject-agent` существует с
  конца октября и в README не упомянут вообще, как и команды `watch`,
  `launch`, `hookcbt`, `cmdinfo`, `exports85`, `frames`, `cmd85`.
- «CI собирает на windows-latest» — workflow пинирует `windows-2022`.

→ README исправлен в этой ревизии; глубина уведена в docs/.

### A2 · P0 · `--help` не знает о половине команд

`PrintUsage` (`src/cli/main.cpp:15-54`) не перечисляет: `launch`, `hookcbt`,
`gitbar`, `cmdinfo`, `exports85`, `frames`, `cmd85`, `exports`, `scan`.
Команды при этом работают. Пользователь узнаёт о них только из README
(который сам отставал — A1).

### A3 · P0 · CLI больше не форвардит `cmd`, `menu`, `menucmd`, `str`

Payload-сторона жива (`wcsncmp(request, "cmd ", 4)` — `v8i_export.cpp:3510`,
`menu`/`menucmd`/`str` там же), но в CLI-диспетчере
(`src/cli/main.cpp:501-506`) этих имён нет: `v8inject cmd 1cv8.exe 2`
печатает usage и выходит с кодом 1. README до этой ревизии документировал
`cmd` как рабочую команду — регрессия прошла незаметно, потому что
рабочим путём стала сессия `attach`.

→ Либо добавить четыре имени в список форварда (2 строки), либо осознанно
документировать «только через attach» — но тогда убрать их из README-примеров.

→ **Закрыто 2026-11-12:** `cmd`, `menu`, `menucmd` и `str` добавлены в список
форварда CLI (см. §7), README приведён в соответствие.

### A4 · P0-закрыто · У вендоренного Capstone не было файла лицензии

`cmake/capstone.cmake:3` обещает «see LICENSE.TXT in the upstream tree», но
файла в `third_party/capstone/` не было — BSD-3-Clause требует сохранения
уведомления при редистрибуции.

→ Закрыто 2026-11-10: заведены `third_party/capstone/LICENSE.TXT` (3-clause
BSD, Copyright (c) 2013, COSEINC) и `third_party/capstone/LICENSE_LLVM.TXT`
(University of Illinois/NCSA — X86-дизассемблер LLVM-производный), в README
добавлена NOTICE-строка в раздел «Лицензия».

### A5 · P1 · 6 коммитов не опубликованы

Вся работа по 8.5 (ранняя подписка, cmd85, receiver-слот 31) существует
только локально. Опубликовать (`git push`) или хотя бы зафиксировать
намерение.

→ **Закрыто 2026-11-12:** вся серия выложена в `origin/main`, релиз `v0.2.19`
опубликован (страница и zip-архивы собраны CI из `RELEASE.md` тега).

### A6 · P1 · Калибровочные константы в коде без таблицы билдов

`kFrameVtblRva = 0x2EFB50` (`v8i_export.cpp:3042`, комментарий
«8.3.27.1989 x64») и смещения x86-цепочки — константы конкретного билда прямо
в коде. Инвариант плана §1.5.7 («никаких хардкодов RVA») частично нарушен.
Предложение P0-3 (файл `data/builds/<version>.json` + загрузка в payload)
остаётся нереализованным. На 8.5 ситуация лучше (runtime-резолв), но
vtable-константы 8.5 (`config.dll+0x2ED3B0`) тоже живут в комментариях/коде.

### A7 · P1 · Единый формат JSON-ответов не введён

Предложение P1-3 плана (`{"status":..., "code":..., "message":...}` +
перечисление кодов) не реализовано: команды отдают разнородные формы.
Усложняет автотесты и разбор логов.

→ **Обновлено 2026-11-13:** конвергенция де-факто случилась: `Guarded` при
крахе команды отдаёт `{"status":"error","message":...}`, 22 из 32
`PutResponse`-ответов payload несут `"status"`, а тест диспетчера закрепляет
наличие `"status"` в ответах пятнадцати команд и `"status":"error"` на
неизвестную команду (`unit_dispatcher.cpp`). Остался формальный контракт
кодов и его документация — приоритет понижен до P2.

### A8 · P1 · Расхождение документации и кода: размер `Command`

`docs/RECON-85.md` §3.3: `Command` = 40 байт (CommandID с выравниванием 8).
Код: `V8Cmd` — 32 байта на x64 (`v8i_export.cpp:1104-1110`, комментарий
«16 + 4 + 4 + 8 = 32»). RECON — исследовательский документ; если кто-то будет
строить структуру по нему (Фаза 4), получится падение. Правку внести в
RECON-85 с пометкой о проверке живым вызовом.

→ **Закрыто 2026-11-13:** обе раскладки разведены и задокументированы в
комментарии к union `V8iPending::u` (`v8i_export.cpp:1167`): `V8Cmd`
32 байта — это передача 8.3, RECON-85 §3.3 описывает 8.5 (`Command`,
40 байт) и там верен; отправитель обнуляет буфер целиком, поэтому обе
интерпретации паддинга читают `param=0` / `object=nullptr`.

### A9 · P2 · `SharedIo`: имя блока предсказуемо, `ERROR_ALREADY_EXISTS` не проверяется

`Client::Open` создаёт блок `Local\v8inject.<pid>`
(`src/host/client.cpp:59-61`) и не проверяет `GetLastError() ==
ERROR_ALREADY_EXISTS`. Любой процесс того же пользователя может создать блок
с таким именем раньше хоста; payload подключится к нему и будет исполнять
чужие команды. Атака локальная и малоправдоподобная, но закрытие дешёвое:
считать `ERROR_ALREADY_EXISTS` фатальной ошибкой Open.

→ **Закрыто 2026-11-12:** блок получает свой дескриптор безопасности (доступ
только у создавшего пользователя и SYSTEM), а существующий блок с тем же
именем считается ошибкой — payload больше не подключается к чужому блоку
(см. §7).

### A10 · P2 · Мусор в локальном `build/*/bin` не покрыт `.gitignore`

Рядом с рабочими DLL лежат копии `v8i_payload.dll.old*` (более 10 штук).
Они не попадают в git (каталог build/ игнорируется целиком), но засоряют
каталог, откуда GUI подставляет payload по умолчанию, и однажды могут
уехать в артефакты CI (`path: build/*/bin/<arch>/*` загружает всё).
Почистить и не плодить `.old*` в bin.

→ **Обновлено 2026-11-13:** `.old*` вычищены; в локальном
`build/x86/bin/x86` остались `v8i_p2.dll`, `v8i_p3.dll`, `v8i_p4.dll` и
`v8i_payload.dll.prev`/`.prev2`. В zip релиза они не попадают (там явно
перечислены четыре файла), в CI-артефакт — попадают. Приоритет P3.

### A11 · P2 · Покрытие тестами неравномерно

- Хуки — хорошо покрыты (hook_smoke, 4 сценария релокации).
- GitBar — E2E только локально (нужна 1С), в CI не идёт (осознанно).
- Цепочка `cmd`/`cmd85` (взаимодействие с 1С) — автотеста нет; это риск

→ **Обновлено 2026-11-13:** половина риска закрыта: протокол хост↔payload и
диспетчер команд payload теперь покрыты юнит-тестами (`unit_protocol.cpp`,
`unit_dispatcher.cpp`) — диспетчер гоняется на настоящем цикле команд без
живой 1С, ответы проверяются на валидный JSON. Осталась живая цепочка
`cmd`/`cmd85` с Configurator: по-прежнему ручная, `tools/check_cmd.sh`
не заведён.

### 9.2 P0 — чинить сейчас

#### A41 · `scan` вызывает чужой vtable вне SEH

`RunScan` (`src/payload/v8i_export.cpp:86-96`) проверяет читаемость
`sizeof(void*)` по адресу и объявляет память `IUnknown*`, после чего
`GetTypeInfoFromUnknown` (`src/common/typeinfo_utils.cpp:12-22`) вызывает
`QueryInterface` через первый qword. Команда приходит из CLI/GUI
(`v8inject scan <exe> <addr>`), а в диспетчере это fallback-ветка
(`v8i_export.cpp:435-441`), то есть **не** под `Guarded`.

Любая опечатка в адресе (или просто буфер данных) — это вызов по мусорному
указателю на потоке payload. Векторный обработчик `FaultLogger`
(`hook.cpp:401-424`) только пишет лог и делает `EXCEPTION_CONTINUE_SEARCH`,
SEH-обёртки вокруг вызова нет — 1С падает. Это единственная команда в
диспетчере, нарушающая правило «каждая команда под SEH».

**Чинить:** обернуть весь `RunScan` в POD-only `__try/__except` (по образцу
`ScanGuarded`) и до вызова проверить, что qword-vtable указывает в
executable-секцию известного модуля (иначе — JSON-ошибка «не похоже на COM»).

#### A42 · Адрес `v8i_probe` в цели считается по дельте от локальной копии

`RemoteLoadLibrary` возвращает базу, найденную **по имени файла** в цели
(`injector.cpp:84-89`), а `StartPayloadThread` загружает тот же путь у себя и
считает адрес как `localProbe + (targetBase − localBase)` (`injector.cpp:226-227`),
затем стартует там поток (`injector.cpp:236-238`).

Если в цели уже живёт **старый** образ payload (хост никогда не делает
`FreeLibrary` в цели — это задокументировано, а после любой сессии DLL
остаётся загруженной), то после пересборки DLL `LoadLibraryW` в цели вернёт
старую базу, а локально загрузится новый файл. RVA `v8i_probe` в них
различаются, дельта становится неверной — поток в 1С стартует по случайному
адресу. Сценарий «пересобрал payload, повторил `probe` к живому 1С» —
штатный цикл разработки; комментарий рядом (`injector.cpp:124-130`) уже
фиксирует, что этот класс ошибки убивал цель 2026-11-15.

**Чинить:** читать RVA экспорта из **целевого** образа (`ReadProcessMemory`
DOS/NT-заголовков по `targetBase` + каталог экспорта), а не переносить
локальную; при несовпадении `TimeDateStamp/SizeOfImage` честно отказывать
(«в цели payload другой сборки — перезапустите 1С»).

#### A43 · Наблюдатель `CreateWindowExW` читает `lpClassName` как строку

`V8iObserveCreateWindow` (`src/payload/platform/platform_commands.cpp:1649-1665`)
берёт `a1` (это `lpClassName`) и делает `wcsncmp`, не проверяя ни
читаемость, ни то, что это строка, а не атом. По контракту Win32
`lpClassName` может быть `MAKEINTATOM(...)`; проект сам документирует, что
на 8.5 главное окно создаётся с **числовым** классом
(`platform_commands.cpp:963-965`). `wcsncmp` по адресу вида `0x8002` — AV на
UI-потоке внутри observer'а. SEH нет: `V8iHookEnter` (`hook.cpp:336-389`)
POD-only, но без `__try`, а VEH только логирует.

**Чинить:** тот же страж, что в CBT-хуке: `cls > (const wchar_t*)0x10000` и
`IsReadable(cls, 96)` до сравнения; лучше — общий безопасный хелпер для
обоих путей.

#### A44 · `cmdinfo` подменяет WndProc кадра мимо `g_subclassBusy`

`V8iSubscribeOnUiThread` (`platform_commands.cpp:839-849`) защищена флагом
именно потому, что «перекрывающаяся попытка захватила бы свой же proc как
original и оставила окно подклассом навсегда». `CmdInfoToJsonA` делает ту же
операцию руками, мимо флага (`platform_commands.cpp:2125-2131`), и сам же
запускает стартовый watcher (`1707-1714`), который ставит тот же подкласс
через `V8iSubscribeOnUiThread` — то есть параллельно с `cmdinfo`.

Гонка: watcher уже поставил `V8iSubclass85` → `SetWindowLongPtrW` в `cmdinfo`
возвращает наш же proc → `g85_origWndProc = V8iSubclass85` → «восстановление»
оставляет окно с нашим proc, а его `orig` указывает на него же
(`platform_commands.cpp:811` — `CallWindowProcW` на себя) → первое же обычное
сообщение даёт бесконечную рекурсию и `0xC00000FD` в UI-потоке 1С.

**Чинить:** свести оба места к одной `V8iSubscribeOnUiThread`; при
`old == (WNDPROC)V8iSubclass85` не подменять/не «восстанавливать», а
отказываться от попытки; владение подклассом — через атомарный флаг.

### 9.3 P1 — реальные дефекты

#### A45 · Таймаут `Call` убивает сессию навсегда

`Client::Call` ставит `kStateRequest` CAS-ом только из `kStateIdle`, а на
таймауте возвращает `false`, не трогая состояние (`client.cpp:201-210`).
Payload дописывает ответ и ставит `kStateResponse` — следующий `Call` снова
видит не-Idle и мгновенно отвечает BUSY. `Close` CAS-ит `Idle→Exit`
(`client.cpp:227`), поэтому `exit` до payload не доходит; хэндлы
закрываются, payload остаётся жив (свой `hMap`), именованный блок
существует — новая сессия к этому pid получает `ERROR_ALREADY_EXISTS`
(`client.cpp:121-129`). Помогает только перезапуск 1С. Дополнительно
`PutResponse` (`v8i_export.cpp:51-59`) безусловно затирает `kStateExit`
ответом, даже если хост уже попросил выгрузку.

Триггеры реальны: CLI даёт тяжёлым командам 15 с, GUI — 20 с, агент — 8-10 с
(`cli/main.cpp:462-465`, `gui/main.cpp:551`, `agent.cpp:177-193`), а
`heapobjects`/`byhwnd`/`memmap` проходят всю память процесса.

**Чинить:** в `Call` после таймаута — grace-догон и восстановление
`Request/Response → Idle`; ввести `seq` в ответ и проверять его; в
`Close` — дождаться Idle, затем `Exit`, а при неудаче возвращать ошибку, а не
молча освобождать хэндлы; в payload — не публиковать ответ поверх
`kStateExit` и завершаться по отсутствию хоста (а не жить вечно в чужом
процессе).

#### A46 · `pe` с >200 экспортами отдаёт невалидный JSON

`inspect_commands.cpp:191-194`:

```cpp
if (shown++) j += ",";
if (shown > 200) break;
```

На 201-м экспорте запятая уже добавлена, элемент — нет; ответ заканчивается
`...},]`. У крупных модулей платформы (core83/config) экспортов сотни, то есть
`v8inject pe 1cv8.exe core83.dll` не разбирается. Второй дефект рядом:
элемент собирается в `char buf[256]` (`195-201`), поэтому манглированное имя
длиннее ~100 символов обрежется посреди JSON-строки.

**Чинить:** `if (shown >= 200) break;` перед запятой (или `first`-флаг),
элемент собирать в `std::string`, добавить `"truncated":true`.

#### A47 · `menu` почти всегда отдаёт невалидный JSON

`AppendItem` (`src/payload/menu.cpp:52-82`) форматирует **весь фрагмент**
(префикс ~45 байт + текст) в `char buf[64]`, поэтому любой пункт с текстом
длиннее нескольких символов обрезается посреди строки. Плюс текст
вставляется через `%s` без JSON-экранирования (а заголовки — пути файловых
баз с `\`), а запятая ставится вызывающим до вызова (`110-113`), хотя
`AppendItem` для разделителя делает `return` (`58`) — получаются `,,` и
висячие запятые. Разделители есть в каждом меню конфигуратора, так что
команда `menu` практически не работает.

**Чинить:** собирать элементы в `std::vector<std::string>` и склеивать через
`join(",")`; текст — через `JsonEscape(WideToUtf8(...))` без фиксированных
буферов; для `AppendWindow` — то же.

#### A48 · `cmdinfo` на 8.5: пропущена запятая

`platform_commands.cpp:2224-2225`: между `"subscribed":%d` и `"qProcFrame":`
нет разделителя. Ответ `cmdinfo` не парсится ровно в том сценарии, ради
которого команда и написана.

**Чинить:** добавить запятую; покрыть `cmdinfo` валидатором `tests/json_check.h`.

#### A49 · На x64 `heapobjects` и `byhwnd` всегда пусты

`FindHeapObjects` читает vtable как `uint32_t` и сравнивает с 64-битными
границами модуля (`memscan.cpp:325-327`), `FindObjectsByHwnd` — так же
(`229-239`). На x64 базовый адрес модуля на практике выше 4 ГБ, поэтому
младший dword настоящего указателя `<= lo` → `continue`. Обе документированные
команды молча отвечают «объектов нет»; юнит-тесты их не вызывают.

**Чинить:** читать машинное слово (`sizeof(void*)`), сравнивать как
`uintptr_t`; добавить x64-тест на собственном образе.

#### A50 · Слот маршала `g_pending` заполняется без блокировки

`V8iCaptureRecv85Late` (`platform_commands.cpp:1198-1203`) и цикл живых проб
кандидатов (`2558-2560`) пишут `g_pending` без `AcquireSRWLockExclusive`,
хотя все остальные пути (`1130`, `2644`, `2772`, `416`, `2735`) держат
`g_pendingLock`. Маршал вызывается минимум с трёх потоков (цикл команд,
воркер выгрузки GitBar, воркер нативного меню), поэтому UI-поток может
выполнить `hasHandler` одного запроса с получателем/функцией другого, а
`V8iRunOnUi` — отчитаться об успехе, не выполнив шаг меню.

**Чинить:** одна внутренняя функция «заполнить слот под локом», все прямые
обращения к `g_pending` — через неё.

#### A51 · У сообщения маршала нет идентификатора запроса

`kV8iCmdMsg` посылается с `wParam=lParam=0` (`platform_commands.cpp:1146`,
`2659`, `2784`), обработчик читает **текущее** содержимое слота
(`222-241`), а признак завершения — один `done`. `SendMessageTimeout` при
таймауте отпускает отправителя, но сообщение доходит и обрабатывается позже
([Raymond Chen, 2011](https://devblogs.microsoft.com/oldnewthing/20110915-00/?p=9643));
к этому моменту слот уже заполнит следующий запрос — UI-поток выполнит его
второй раз (повторная выгрузка/коммит/удаление) или засчитает «успех»
невыполненного шага.

**Чинить:** поле `reqId` в слоте, передавать его в `wParam`, в обработчике
игнорировать несовпавшие (и `done` выставлять по `reqId`); после таймаута
помечать слот «отравленным» до подтверждения.

#### A52 · Хуки нативного меню ставятся до проверки версии и без защиты наблюдателя

`MMWorkerInner` ставит хук `1cv8.exe+0xBFCB0` сразу при старте
(`mainmenu.cpp:1288-1294`) — **до** `MMNativeMenuEnabled` (1297) и
`MMSupported` (1302), хотя комментарий у константы (`146-149`) говорит
«на прочих версиях пункт не добавляется». `MMSupported` пропускает всю семью
`\8.3.27.`, а RVA откалиброван на 8.3.27.2342 x64 — на другой сборке той же
семьи хук встанет в чужую функцию. Наблюдатель `MMObsTakeProc`
(`mainmenu.cpp:185-201`) первым делом делает `*(const GUID*)a1` и
`LogLine` без `IsReadable`; вызов из thunk — без SEH. Цена — падение 1С или
порча состояния.

**Чинить:** ставить хуки только после `MMSupported` и `nativemenu`, проверять
пролог целевой функции (как в `V8iInstallCreateWindowHook`), в наблюдателе —
`IsReadable(a1, sizeof(GUID))` и лог один раз через `InterlockedCompareExchange`.

#### A53 · `[git] nativemenu=0` не читается из UTF-16 ini

`MMNativeMenuEnabled` (`mainmenu.cpp:1071-1093`) читает файл как сырые байты и
ищет ASCII-подстроку `strstr`. `v8i::IniSet` создаёт файл с BOM
`0xFF 0xFE` и пишет UTF-16 (`ini.cpp:27-77`), а в UTF-16 после BOM идёт
`'[' 0x00` — `strstr` останавливается на первом NUL. После первого же
сохранения настроек payload'ом аварийный выключатель, добавленный именно
после зависания 1С, перестаёт работать.

**Чинить:** читать через `v8i::IniGet` (профильные API здесь сознательно не
используются — заменить на ручное чтение с определением BOM) либо писать
ini в UTF-8 и читать везде одинаково.

#### A54 · `git status --porcelain`: путь получает символ статуса

`ListDlgSel` (`src/payload/gitbar/git_lists.cpp:87-96`) берёт
`line.substr(line.find(' ') + 1)`. Для самой частой строки ` M path` первый
пробел стоит по индексу 0, поэтому в `git add/reset/checkout --` уходит путь
`M path` (`129-135`) → `pathspec did not match any files`. Работают только
`??`, `M `, `A ` и т.п.; «файл изменён, но не проиндексирован» — типичное
состояние выгрузки — не работает вообще.

**Чинить:** брать фиксированные два символа статуса
(`line.substr(3)` для `XY `) либо `status --porcelain -z`.

#### A55 · Вложенные циклы GitBar проглатывают `WM_QUIT`

`PromptText` (`gitbar.cpp:423-429`), `ShowSettings`, `ShowList`, `ShowGitLog`
крутят собственный `GetMessageW` по всей очереди потока и на `0` просто
`break` — `WM_QUIT`, отправленный из `WM_DESTROY` бара (`gitbar.cpp:1069-1081`),
исчезает. `g_bar.hwnd` обнуляется только после выхода из цикла `BarThread`
(`1186`), поэтому:

- `gitbar hide` во время диалога закрывает окно, но поток остаётся жить;
- следующая `gitbar` команда видит `g_bar.hwnd` и отвечает `already shown`
  (`1233-1235`), панель больше не показать;
- `MenuShutdown()` не вызывается — оверлей «GitBar» остаётся в ряду меню.

**Чинить:** в каждом вложенном цикле при `GetMessageW()==0` —
`PostQuitMessage((int)msg.wParam)`; `g_bar.hwnd`/`thread` обнулять в
`WM_DESTROY`; в `GitBarCommandToJson` проверять `IsWindow`.

#### A56 · `watch` без `--once` срабатывает ровно один раз

`RunWatch` выставляет `fired = true` (`cli/main.cpp:279-283`) и в ветке
перевзвода делает только `lastActive = 0` (`306-307`). Условие `!fired`
после первого срабатывания всегда ложно; процесс висит до `--timeout-sec`
(по умолчанию 10 минут) и печатает `timeout`, хотя документация обещает
повторные срабатывания.

**Чинить:** в rearm-ветке `fired = false; matchCount = 0;` (для `--once` —
`break`), плюс ограничить рост `PathCache` (сейчас кешируются и неудачные
`str` как пустой путь).

#### A57 · `IsProcess64` возвращает разрядность хоста (A18 переоткрыт)

`procs.cpp:73-75` смотрит `nativeMachine` — по документации это **хост**;
тип процесса — `processMachine`. На 64-битной Windows любой процесс
объявляется 64-битным. Проверено эмпирически на этой машине: 32-битный
`cmd.exe` → `procMachine=0x014C, nativeMachine=0x8664`; 64-битный →
`0x0000/0x8664`. Код в обоих случаях вернёт `true`. GUI спасает
`IsPe64(path)` в `ListProcesses`, но CLI `v8inject modules` врёт, а
фолбэк для недоступного пути снова выберет x64-payload для x86-цели.

**Чинить:** `is64 = processMachine == UNKNOWN ? (nativeMachine == AMD64 ||
nativeMachine == ARM64) : (processMachine == AMD64 || processMachine == ARM64)`;
тест на 32- и 64-битной сборке.

#### A58 · `git -C dumpdir` без проверки корня репозитория

`DoCommit`/`DoPush`/`DoPull`/`DoFetch` (`gitbar.cpp:452-458`, `653-736`)
работают с каталогом из настроек напрямую, в отличие от списков и истории
(`git_lists.cpp:291`, `git_log.cpp:1219`), где проверяется `.git`.
Если `dumpdir` не репозиторий, но лежит внутри чужого репозитория
(типично: `E:\work\proj\dump`), `git -C dir add -A` + `commit` + `push`
тихо добавят и отправят файлы **чужого** проекта.

**Чинить:** перед операцией проверять `git -C dir rev-parse --show-toplevel`
и требовать совпадения с `dumpdir` (нормализованно); если `.git` нет —
предлагать `init`.

#### A59 · Thunk-и портят аргументные регистры перехваченной функции

x64 (`hook_thunk_x64.asm:31-59`) сохраняет `rax/rcx/rdx/r8/r9/rbp`, но не
`xmm0-3`: `V8iHookEnter` — обычная C++-функция, для неё SSE-регистры
volatile, поэтому после возврата трамплин может доиграть пролог с уже
испорченными float/double-аргументами. x86 (`hook_thunk_x86.asm:40-45`) берёт адрес
трамплина в `ecx/edx` **после** `popad`, поэтому `__thiscall`-функция
получает `this` = `HookCtx*`, а `__fastcall` — мусор. Хуки ставятся на
внутренние функции 1С по RVA (thiscall), так что это не теория; тесты
используют `extern "C"`-функции и дефект не видят.

**Чинить:** сохранять/восстанавливать `xmm0-5` (64 байта уже помещаются в
кадр thunk-а); на x86 — `jmp dword ptr [esp-4]` (или через `eax`), не
затрагивая аргументные регистры; добавить в `hook_target.cpp` цель
`__thiscall` и цель с `double`.

#### A60 · Прогулка по кадрам читает за проверенный диапазон

`hook.cpp:366-376` проверяет `IsReadable(fp, 8)`, затем читает `[fp]` и
`[fp+8]`. На x64 `entryEb` — это `rbp` на входе в функцию, а MSVC x64 не
использует frame pointer, поэтому значение произвольное; если оно указывает
на последние 8 байт отображения, второе чтение даёт AV в потоке 1С (SEH в
`V8iHookEnter` нет, VEH только логирует).

**Чинить:** `IsReadable(fp, 2*sizeof(uintptr_t))`; обернуть прогулку в
POD-only `__try`; на x64 для цепочки использовать `RtlLookupFunctionEntry`/
`StackWalk64`, а не `rbp`.

#### A61 · GUI: цикл настроек съедает `WM_QUIT` → процесс-зомби

`DoGitbarSettings` (`gui/main.cpp:795-802`) крутит свой `GetMessageW` для всех
окон потока, владелец не отключается. Пользователь закрывает главное окно —
`WM_DESTROY` делает `PostQuitMessage(0)` (`1022-1025`) — вложенный цикл
вычитывает `WM_QUIT` и выходит, после чего внешний цикл
(`1064-1070`) блокируется навсегда: окон нет, выйти нечем. Плюс всё время
диалога можно нажимать «Инжектировать» на главном окне.

**Чинить:** `EnableWindow(g_hwnd, FALSE)` на время диалога; при
`GetMessageW()==0` — `PostQuitMessage((int)msg.wParam)` перед выходом.

#### A62 · Агент навсегда запоминает неудачу и не замечает новый PID

`g_injected`/`g_failed` (`agent.cpp:52-53`) только пополняются
(`172`, `181`, `185`) и никогда не чистятся; проверка — `204`, `259`.
Транзиентный сбой `Open` (1С ещё стартует, политика прав) навсегда
отключает автовнедрение в этот экземпляр; при переиспользовании PID новая
1С молча пропускается как «уже внедрена».

**Чинить:** хранить `(pid, FtCreationTime)` или чистить наборы по актуальному
списку процессов; для `g_failed` — счётчик попыток с backoff.

#### A63 · Гонка инициализации лога в payload

`diag.cpp:18-38`: `g_csReady`/`g_cs` инициализируются лениво без
синхронизации; два потока могут войти в окно между проверкой и
`InitializeCriticalSection` и повторно инициализировать уже используемую
секцию. `SetLogDirectory` пишет `g_logPath` без блокировки, а `LogLine` читает
его из других потоков. Payload многопоточен (цикл команд, воркеры ранней
подписки, хуки, GitBar), а `InitPayloadLog(g_io->logDir)` вызывается уже
после старта ранних потоков — окно реально.

**Чинить:** `INIT_ONCE`/статический `SRWLOCK` для лога; путь — под тем же
локом или только до старта потоков.

#### A64 · GUI пишет настройки GitBar мимо `v8i::IniSet`

`gui/main.cpp:577-579` вызывает `WritePrivateProfileStringW` напрямую, без
`EnsureFolderOf`/`EnsureUnicodeFile` и без проверки результата, хотя
`v8i_common` слинкован. На чистом профиле (панель ещё не показывали)
каталога `%APPDATA%\v8inject` нет — запись падает с `ERROR_PATH_NOT_FOUND`,
введённые значения теряются, а лог печатает «сохранены» (`804`). Когда
каталог есть, файл создаётся в ANSI без BOM — ровно то, что лечил A19.

**Чинить:** использовать `v8i::IniSet/IniGet` и писать «сохранены» только при
успехе всех записей.

#### P0 — чинить сейчас

##### A116 · Кучевые строки описаний команд уходят платформе с refCount=1

`MMSetLong` (`mainmenu.cpp:476-487`) выделяет строку **своим** `malloc` и
пишет её в слоты v8string описания команды с refCount = 1:

```cpp
unsigned char* data = (unsigned char*)malloc(len * 2 + 6);
if (!data) return;
*(unsigned*)data = 1;
memcpy(data + 4, text, (len + 1) * 2);
memset((void*)dst, 0, 24);
*(unsigned char**)dst = data;
```

Единственный потребитель — `MMSetCommandTextLong` (`mainmenu.cpp:500-502`,
живой путь `:1021`): 14 действий × 4 слота = 56 кучевых строк в
platform-owned объекте. При этом соседний URL-путь (`:715-719`) решает ту
же проблему осознанно, и собственный комментарий проекта фиксирует цену:

```cpp
// Конструктор копирует строку; refCount=2 не даёт платформе освободить
// наш блок своим аллокатором (у payload и 1С разные CRT) — блок остаётся
// висеть до выхода из процесса (24 байта на пункт).
```

Как только платформа освобождает описание (перестроение меню, закрытие
конфигурации), счётчик падает до 0 и **1С вызывает `free` своего CRT на
указатель из кучи payload** — порча кучи 1С, отложенный краш. Если
платформа эти блоки не освобождает до выхода процесса, цена сводится к
утечке — но признание риска в соседнем пути проекта означает, что
Release-путь реален. Нативное меню в v0.8.1 включено по умолчанию.

**Чинить:** в `MMSetLong` принять refCount параметром (для
`MMSetCommandTextLong` ставить 2, как в `MMSetDescrUrl`) — правка на
несколько строк; приёмка на живой 8.3.27.2342: построить меню, закрыть и
заново открыть конфигурацию, поработать с панелью.

#### P1 — реальные дефекты

##### A99 · AV при снятии хука под приостановкой оставляет потоки 1С замороженными

`HookRemove` после `Suspend()` (все прочие потоки заморожены) читает пролог
цели без стража читаемости (`hook.cpp:1046-1049`):

```cpp
uint8_t now[kMaxStolen] = {};
memcpy(now, (const void*)ctx->target, ctx->stolen);
if (memcmp(now, ctx->patch, kPatchLen) != 0) {
```

Между установкой и снятием модуль с хуком мог быть выгружен (хук на плагин
или чужую DLL) — чтение decommitted-страницы даёт AV. VEH только логирует;
SEH-обёртки вокруг окна приостановки нет, а раскрутка SEH не вызывает
деструкторы C++-объектов промежуточных кадров (это зафиксировано в самом
A69) — `~Suspender` с `ResumeAll` не выполнится, **все приостановленные к
этому моменту потоки 1С остаются замороженными навсегда**. Хуже: выход
payload вызывает `HookRemoveAll` (`v8i_export.cpp:704-708`) вне `Guarded` —
там тот же AV роняет процесс.

**Чинить:** после успешного `Suspend` — `IsReadable(ctx->target, stolen)`,
при отказе `ResumeAll` + отказ снятия (под приостановкой ничего не
выполняется, TOCTOU-окно схлопывается); вынести verify+restore в POD-only
хелпер с `__try`, который в `__except` сам вызывает `ResumeAll`; то же —
для exit-пути `HookRemoveAll`.

##### A106 · `scan` — единственная команда вне FitReply/Guarded

Fallback-ветка диспетчера (`v8i_export.cpp:678-689`) собирает ответ прямо:

```cpp
TypeInfoReport rep;
const ScanStatus st = RunScan(g_io->request, rep);
...
PutResponse(ToJson(rep));
```

Все прочие команды идут через `Guarded` → `FitReply` (A69): непомещающийся
ответ превращается в JSON-ошибку. Здесь же `ToJson(rep)` имеет дефолт
`pretty = true` (переносы и отступы, ×2–3 к размеру), `ScanTypeInfo` не
ограничивает `funcs` (до 65535), а `V8iPublishReply` при переполнении
**молча обрезает** документ посреди строки (`v8i_export.cpp:320-322`) и
публикует его. Вторая грань: сборка `std::string` вне SEH-кадра `RunScan`
и вне `catch` — `std::bad_alloc` не ловит никто → `std::terminate` →
падение всего процесса 1С. `v8inject scan 1cv8.exe <адрес крупного
COM-объекта>` — штатный сценарий реверса.

**Чинить:** обернуть ветку в `Guarded(L"scan", …)` (FitReply и catch
появятся бесплатно), отдавать `ToJson(rep, /*pretty=*/false)`; убрать
«тихую» обрезку в `V8iPublishReply` — после починки она недостижима, а
лучше отказ, чем обрезанный документ.

##### A156 · `watch` не срабатывает никогда: парсер записи трассы не согласован с форматом

Парсер в `RunWatch` (`cli/main.cpp:264-265`) требует `"args":[` в пределах
60 символов от `"hook":`:

```cpp
size_t a = resp.find("\"args\":[", h);
if (a == std::string::npos || a > h + 60) break;
```

Фактическая запись трассы (`hook.cpp:1371-1377`) сериализуется как
`{"seq":N,"hook":H,"tid":T,"tick":K,"ret":"0x<16 hex>","args":[…]}` — между
`"hook":` и `"args":[` лежат `"tid"`, `"tick"`, `"ret"`, что даёт
`50 + len(hook) + len(tid) + len(tick)` символов. При типичных tid = 4–5
знаков и tick = 8–10 (GetTickCount64 — время с загрузки) это 63–67 > 60:
условие срабатывает на первой же записи, парсер выходит из цикла, `any`
остаётся false, `lastSeq` не двигается — на каждом опросе ответ разбирается
заново и отбрасывается. Документированная команда «триггер на выгрузку
конфигурации для git-конвейера» не срабатывает никогда (единственный шанс —
машине, загруженной секунды назад, с tid из одной цифры). Юнит-тесты
гоняют только `WatchGate`/`WatchPathCache`, парсер в них не входит.

**Чинить:** поднять границу до реального максимума заголовка записи
(~160) или убрать её вовсе; правильнее — вынести разбор записи в
тестируемую функцию рядом с `WatchGate` и покрыть тестом с настоящим
ответом `trace`.

### 10.5 Что проверено и корректно

Положительные результаты шести проходов, которые не надо переделывать:

- **Хуки**: формула переноса rip-относительного операнда перевыведена и
  подтверждена стендом A75; переназначение внутрилепрестольных переходов и
  отказные ветки пролога корректны; кадры трамплинов x64/x86 сходятся с
  asm побайтово, `xmm0-5` сохраняются, выравнивание x86 по конвенции
  (A59/A92 закрыты чисто); восстановление только своих байтов, дубли и
  перекрытия отсекаются (A71); кольцо трассы 64-битное с копией записи
  между двумя чтениями `seq` (A90); бюджет `trace` (A70); `Suspender` не
  аллоцирует в окне приостановки (A72); читаемость в `disasm`/`xref`
  (A84).
- **Протокол**: все писатели слова состояния разведены (CAS только у
  владельцев переходов), барьеры через `Interlocked*` на обеих сторонах;
  ABI-версионирование с `static_assert`-арифметикой; сторож смерти хоста
  корректно завершается до unmap; DACL fail-closed; `unit_protocol` — 14
  сценариев на реальном цикле команд.
- **Диспетчер**: SEH-дисциплина — все команды кроме `version`, `exit` и
  scan-fallback (A106) в `Guarded` с явным `bad_alloc`; гейт `scan` (A41)
  и пределы сканеров (A83) на месте; проходы по памяти идут
  `VirtualQuery` без нулевого прогресса.
- **Маршал и платформа**: `pending_slot` — единственный исполнитель,
  `reqId`, seqlock-копии (A50/A51); перевалидация 8.3-кадра перед каждым
  вызовом с cooldown; приёмник 8.5 перепроверяется перед каждой отправкой
