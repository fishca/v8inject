# План RE: служебный реестр сервисов Конфигуратора

Цель — найти способ получить `ICommandService` из процесса Конфигуратора
для нативного пункта меню «GitBar» (`src/payload/mainmenu.cpp`).

**Статус (2026-11-17): Фазы R1–R4 выполнены. Нативный пункт «GitBar» —
отдельное подменю верхнего меню между «Сервис» и «Окна». В нём зарегистрированы
14 действий с полными русскими названиями и тремя групповыми разделителями.
Live на 8.3.27.2342 x64 подтверждены открытие «Настроек» и «Рабочей копии»,
Release-сборки x86/x64 с `/WX` и все тесты на обеих архитектурах.**

**2026-11-18: Фаза R5 — пункты подменю получили те же картинки, что и панель
GitBar (см. §7).**

## 2. Две ошибки, объяснившие все прошлые отказы

1. **MMGuid**: парсер «{8-4-4-4-12}» читал Data4 фиксированными окнами по 2
   символа — а тире стоит и внутри Data4 («…-9DCF-0050BAE2BC79»). Все байты
   Data4 съезжали: gq1 = 0xC72BAE0B0500CF9D вместо 0x79BCE2BA5000CF9D.
   **Каждый GUID модуля (IID сервиса, группа, рамка, CLSID) был испорчен** —
   все getService/QI/bandById из payload возвращали null во всех прошлых
   прогонах. Исправлено: чтение ровно 32 hex-цифр с пропуском тире.
2. **addSource отсутствовал**: MMStepSource создавал CommandInterface,
   клал панели (addBand) и завершал (finish), но не отдавал источник
   менеджеру (слот 10, MM_REBUILD=1 — v8snack mainmenu.as шаг 4). Панели
   в карте менеджера не появлялись. Исправлено.

## 3. Фаза R1: дизассемблировка getService — ВЫПОЛНЕНА

РеализацияgetService (слот 14) и формат реестра описаны в §1. Путь

## 4. Фаза R2: получение ICommandService — ВЫПОЛНЕНА

Реализация в `mainmenu.cpp` (`MMScanRegistry`, опрос каждые 10 с):
1. Скан кучи по vtable SCOM_Process (qword, шаг 8 байт) → кандидаты;
2. У первого экземпляра с записью {8F885821-…} в реестре берём сервис
   (чтение `[node+0x38]`, только память, без вызовов vtable);
3. Менеджер панелей — по содержимому: скан объектов класса менеджера
   (vtable frame.dll+0xB097F0) и поиск в карте панели {MM_FRAME}/52
   (`MMFindMenuManager`); fallback — менеджер из `[svc+0xD0]`, если у
   него непустые источники.
Критерий `svc != null && manager != null` выполняется за один опрос
после построения меню (~3 с после старта дизайнера).

## 5. Фаза R3: нативный пункт — ВЫПОЛНЕНА

Цепочка на живом svc (8.3.27.2342):
1. Образцы пунктов — найдены (верхнее меню {MM_FRAME}/1, панель «Сервис» /52);
2. registerCommands — 15 команд: popup «GitBar» и 14 действий. Короткий
   заголовок popup записывается в SSO; полные названия действий — в четыре
   текстовых поля описания каждой команды в форме кучевой `v8string`;
3. Источник: createByClsid → addBand ×2 → finish → **addSource(MM_REBUILD=1)**.
   Popup содержит 14 действий и 3 разделителя `{9D0A2E40-…}/0` перед
   «Забрать изменения», «Ветки…» и «Настройки…»;
4. Панель {8B4A6E2F-…}/1 влилась в карту менеджера (36→37 записей), пункт
   «GitBar» — в панели верхнего меню {MM_FRAME}/1 с весом **18.5**
   («Сервис» = 18.0, «Окна» = 19.0 — отдельное подменю между ними, по
   запросу пользователя; изначально пункт добавлялся внутрь «Сервиса»);
5. Перехваты updateState/hasHandler/transmitCommand на приёмнике рамки.
   Команды 11–24 преобразуются в обычные GitBar-действия 1–14 и передаются
   окну бара через `PostMessage`; «Настройки» используют отдельное отложенное
   сообщение. Модальные диалоги не открываются внутри `transmitCommand`.
Плюс атомарность шагов (повтор не дублирует регистрацию/источник),
мьютекс «один строитель на процесс», SEH на каждую попытку дискавери/скана.

## 7. Фаза R5: картинки пунктов нативного меню — ВЫПОЛНЕНА (2026-11-18)

Пункты подменю «GitBar» теперь несут те же 16×16 глифы, что и панель GitBar
(набор qtv8reader metadata-icons, MIT, см. §7a). Реверс (live 8.3.27.2342 x64):

1. `ICmdDescription::image()` (слот 5) сначала отдаёт поле-кэш `descr+0x80`;
   если оно пусто — достаёт `core::URL` из `descr+0x40` (24-байтная v8string +
   вектор разбора + флаги) и просит сервис картинок (image.dll) построить
   `IImage` по URL. `registerCommands` картинку не передаёт, поэтому после
   регистрации описание пустое — пункты рисуются без иконок.
2. В описание можно положить любой URL, собранный штатным конструктором
   `core::URL::URL(const v8string&, bool)` (иначе поля разбора URL невалидны и
   платформа картинку не строит); готовый `IImage` кэшируется сервисом.
   Проверены `v8res://…` и `file:///…`.
3. Итог: payload пишет PNG-глифы (те же файлы, из которых собран `icons.h`)
   в `%TEMP%\v8inject-icons` и подставляет в описания команд `file:///`-URL.
   Глифы совпадают с панелью пиксель-в-пиксель и не зависят от ресурсов
   конкретной сборки; `file:///` выбран и по лицензионной причине — картинки
   из ресурсов 1С (`v8res://…`) нельзя распространять в составе проекта.
4. Адрес конструктора URL резолвится по таблице экспортов core83 **в памяти**
   (payload не зависит от файлов на диске): скан PE-заголовка загруженного
   модуля и поиск экспорта `??0URL@core…ale@@…BasicString…_N@Z`; RVA
   различаются по сборкам (2342 x64 — 0x2D3840, 1989 x64 — 0x2D2A60,
   1989 x86 — 0x289FF0, запасная таблица). Шаг «иконки меню» идемпотентен,
   стоит после addSource; при любой ошибке меню просто остаётся без картинок.
5. Проверка (live 8.3.27.2342 x64): 15/15 описаний получили URL; подменю
   рисует все картинки — выгрузка (×2), init, клонирование/ветки, коммит,
   push, pull, fetch, stash, теги, рабочая копия, история, настройки.
   Release x64/x86 собираются, CTest 4/4 на обеих архитектурах.

## 7a. Иконки: набор qtv8reader (metadata-icons, MIT) вместо картинок из ресурсов 1С (2026-11-19)

Изначально 12 глифов панели были вырезаны из ресурсов платформы
(`core83_root.res`, `mngcore_root.res`, `core85_root.res`, …). Такие картинки
— часть продукта 1С, и распространять их в архивах проекта неправильно.
Иконки заменены на открытый набор из соседнего проекта qtv8reader:

- 16-пиксельные PNG взяты из `fishca/qtv8reader`,
  `resources/icons/metadata`: это открытый набор **metadata-icons**
  (`zerobig/vscode-1c-metadata-viewer`, MIT, Copyright (c) 2023 zerobig and
  contributors), перекрашенный qtv8reader в палитру 1С; исходники 15 выбранных
  глифов, текст лицензии и таблица «роль → файл» лежат в
  `src/payload/icons/qtv8reader/` (`LICENSE-METADATA-ICONS.txt`,
  `ATTRIBUTION.md`);
- `tools/select_icons.py` раскладывает выбранные файлы по ролям
  (`src/payload/icons/<role>.png`), `python tools/gen_icons.py` собирает
  `icons.h` (premultiplied BGRA) и `icons_png.h` (для `file:///`-URL нативного
  меню) — панель и подменю используют одни и те же файлы;
- глифы типов метаданных подобраны под смысл действий: `document` — выгрузка
  исходников, `dataProcessor` — расширение, `constant` — создание репозитория,
  `externalDataSource` — клонирование, `accountingFlag` — коммит,
  `exchangePlan` — push, `businessProcess` — pull, `ws` — fetch,
  `group` — ветки, `settingsStorage` — stash, `filterCriteria` — теги,
  `extDimensionAccountingFlag` — рабочая копия, `scheduledJob` — история,
  `sessionParameter` — настройки, `subsystem` — сам пункт «GitBar»;
- назначение и источник каждой роли зафиксированы в
  `src/payload/icons/SOURCE.json`; MIT-лицензия требует сохранять уведомление
  об авторских правах — оно лежит в `qtv8reader/LICENSE-METADATA-ICONS.txt` и
  продублировано в README/RELEASE.md.
