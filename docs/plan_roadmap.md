# План развития v8inject — реализация внешнего анализа (2026-11-14)

Источник: «Анализ проекта v8inject» (ChatGPT, 14.11.2026) — статический обзор
репозитория через GitHub. Документ переводит рекомендации анализа в план работ
в терминах текущего кода: каждая фаза сверена с исходниками и с ревизией
[AUDIT.md](AUDIT.md) (номера находок A* сохраняются для сквозной трассировки).

Порядок этапов — из анализа: **стабильность → совместимость → архитектура →
продукт**. Сначала предсказуемое поведение при сбоях, затем проверяемые
адаптеры сборок 1С, затем разбиение больших модулей, и только потом новые
функции GitBar и внешний API автоматизации.

## 1. Правила всего плана

1. **Каждая фаза — отдельная ветка и PR** (`stability/*`, `compat/*`,
   `arch/*`). Прямые коммиты в `main` — только для документов.
2. **Сборка x86+x64 Release и `ctest` — зелёные после каждого шага.**
   Фазу ведут маленькими коммитами: перенос кода без изменения поведения
   и правка поведения — никогда в одном коммите.
3. **Инварианты payload не пересматриваются** (ревизия 2026-11-08, §3.1):
   каждая команда под SEH, `__try` только с POD, `SRWLOCK` вместо
   `std::mutex`, никаких диалогов CRT в DllMain, протокол — POD-only.
4. **Юнит-тесты не требуют живой 1С.** Всё, что проверяется на живой
   платформе, оформляется как `tools/check_*.sh` и план живой проверки в
   [VERIFY.md](VERIFY.md) — и выполняется перед релизом.
5. **Документация едет вместе с кодом.** `RELEASE.md` коммитится **до**
   тега (находка A34); заметки релиза не дополняются после тега.
6. Релиз закрывает этап: `v0.2.25` — этап 1; `v0.3.0` — этап 2;
   `v0.4.0` — этап 3. Порядок номеров условен, важнее состав.

Трудоёмкость: **S** — до дня, **M** — 2–3 дня, **L** — порядка спринта.

## 3. Этап 1. Стабильность (первый приоритет)

Цель этапа: **предсказуемое поведение при сбоях и многопоточной работе** —
формулировка анализа. Ветка `stability/injection-and-hooks`.

### Ф1.1 Внедрение: не освобождать удалённую память при таймауте (P0, S)

**Проблема.** `RemoteLoadLibrary` (`injector.cpp:27-62`) ждёт удалённый
поток 15 секунд; на `WAIT_TIMEOUT` выполняется `VirtualFreeEx` строки 51 —
буфер с путём DLL освобождён, а поток ещё может читать этот адрес.
Ещё один сценарий: `LoadLibraryW` успела загрузить DLL, но таймаут слетел —
хост сообщает «не внедрилось», хотя payload уже в процессе.

**Шаги.**

1. Разделить исход `wait`:
   - `WAIT_OBJECT_0` → как сейчас: проверить exit-code, освободить буфер
     (`VirtualFreeEx`), готово;
   - `WAIT_TIMEOUT` → **буфер не освобождать**. Сначала повторно
     `FindModuleInProcess(hProc, dllPath)`: если модуль появился — считать
     внедрение успешным (заполнить `baseOut`, лог «timeout but loaded»).
     Если нет — вернуть отказ с диагностикой «injection hung», оставив
     выделение в цели (утечка нескольких сотен байт против риска исполнения
     освобождённой памяти — осознанная цена, задокументировать комментарием);
   - `WAIT_FAILED` → отказаться, память освободить (поток не стартовал).
2. Дополнить `LogLine` стадией и решением («freed» / «leaked on timeout» /
   «found after timeout»), чтобы зависшее внедрение диагностировалось по
   логу, а не по отсутствию лога.
3. Попутная чистка: `Client::ReleaseHandles` (`client.cpp:71-83`)
   освобождает `remoteName_`/`remoteArgs_`, но `StartPayloadThread` уже
   не создаёт remote-строк (payload выводит имя блока из своего PID,
   `injector.cpp:176-178`) — мёртвые поля убрать из подписи
   `StartPayloadThread` и `Client` (правка с обновлением трёх вызовов:
   cli/gui/agent уже линкуют общий файл, правка только в заголовке и
   client.cpp).
4. Политика ретраев для агента: после зависшего внедрения не повторять
   попытку в тот же pid до перезапуска 1С (в `agent.cpp` — один бит
   «pid промазан»).

**Тест.** Автотест на реальный таймаут невозможен без чужого процесса;
регресс закрывается: (а) `hook_smoke` — успех пути, память освобождается;
(б) юнит-тест на новую логику решения по `wait`-коду, вынесенную в
чистую функцию `RemoteLoadOutcome(wait, code, modulePresent)` в
`v8i_common` — таблица случаев (ok / timeout+loaded / timeout+not-loaded /
failed).

**Критерий приёмки.** В `injector.cpp` нет вызова `VirtualFreeEx`,
достижимого при `WAIT_TIMEOUT`; юнит-тест решений зелёный; `hook_smoke`
3/3 на обеих разрядностях.

### Ф1.2 Внедрение: явное разрешение `LoadLibraryW` в цели (P1, S)

**Проблема.** Адрес берётся локально (`injector.cpp:32-33`) в расчёте на
совпадение баз kernel32. Практически оправдано (ASLR per-boot), но ничем
не проверяется: при несовпадении `CreateRemoteThread` вызовет чужой адрес
в процессе 1С.

**Шаги.**

1. После `OpenProcess` найти удалённую базу kernel32
   (`EnumProcessModulesEx`, техника уже есть в `FindModuleInProcess` —
   вынести общий `ModuleBaseInProcess(hProc, name)`).
2. Скорректировать адрес: `remoteAddr = localFn − localK32 + remoteK32`.
   Если удалённая kernel32 не найдена или разница уродлива — отказ с новой
   стадией `kStageResolveKernel32` и внятным `lastError`.
3. Лог печатает обе базы и дельту.

**Тест.** `hook_smoke` проходит реальный кросс-процесс инжект — этого
достаточно; лог-строка подтверждает вычисление дельты.

**Критерий приёмки.** Адрес удалённой функции никогда не используется без
проверенной дельты; `hook_smoke` 3/3.

### Ф1.3 IPC: fail-closed дескриптор безопасности (P1, S)

**Проблема.** Если `MakeBlockSecurityDescriptor` не удался
(`client.cpp:101-107`), блок создаётся с DACL по умолчанию — любой процесс
сеанса сможет притвориться payload'ом (A9 закрыл чужое подключение
существующего блока, но fallback на слабые права остался).

**Шаги.**

1. Убрать ветку fallback: SD не построился → `lastError` «не удалось
   построить дескриптор безопасности блока», `OpenBlock` возвращает false.
   Принцип из анализа: невозможность установить ожидаемые права — ошибка.
2. Проверить, что payload-сторона не страдает: она открывает блок по имени
   от имени того же пользователя — DACL это разрешает (юнит-тесты протокола
   уже открывают блок, созданный с DACL, и остаются зелёными).

**Тест.** Отдельный юнит не нужен (нечем подменить `OpenProcessToken`);
фиксируется поведением существующих `unit_protocol`. В `unit_protocol`
добавить проверку, что `second.OpenBlock` на существующий pid по-прежнему
отказывается (регресс A9 не потерять).

**Критерий приёмки.** Нет пути создания блока без DACL; тесты зелёные.

### Ф1.4 Хуки: аудит жизненного цикла и стресс-тест (P0, M)

**Проблема.** `Suspender` (`hook.cpp:161-224`) приостанавливает потоки
процесса на время переписывания пролога. Риски из анализа: взаимоблокировка
(остановленный поток держит heap/loader lock — в коде уже есть комментарий
`hook.cpp:224` и осторожность при резервировании памяти), гонка с потоками,
созданными во время паузы, поток уже исполняет трамплин, снятие хука.
Автотестов на это нет.

**Шаги.**

1. **Аудит-лист** (зафиксировать в комментарии к `Suspender` и в
   ARCHITECTURE.md): что происходит с (а) потоком, созданным между
   снимком потоков и патчем (он не приостановлен и может прыгнуть в
   переписываемый пролог); (б) потоком, стоящим внутри трамплина при
   снятии хука; (в) восстановлением оригинальных байт, когда другой поток
   в это время исполняет пролог. По каждому — либо доказательство защиты,
   либо смягчение:
   - (а) минимальное смягчение: после патча короткая пауза и повторный
     снимок (новые потоки до патча могут исполнить уже патченный пролог —
     безопасно; проблема только в окне между снимком и записью). Фиксация
     остаточного риска в документе — приемлемо для диагностического
     инструмента;
   - (б) уже закрыто: трамплин не освобождается при unhook
     (README «Хуки», `hook.cpp`);
   - (в) атомарная запись патча: на x64 пролог заменяется ≤16 байтами —
     рассмотреть одну межпроцессно-видимую запись 8/16 байт вместо
     последовательности; если не применимо — задокументировать окно.
2. **Стресс-тест** `tests/hook_stress.ps1` + доработка
   `tests/hook_target.cpp` (режим `--stress`): N рабочих потоков крутят
   целевую функцию, параллельно сценарий выполняет M циклов
   hook → проверка записи вызова → unhook; в конце — сверка счётчика
   вызовов с ожидаемым и проверка, что цель жива и байты пролога
   восстановлены. Целевые параметры: 4 потока × 20 циклов.
3. Включить в CI как `hook_stress` с таймаутом 300 с (обе разрядности).
4. Сценарий «завершение цели во время операций» — отдельный прогон
   стресс-теста с kill цели в середине цикла; ожидание: хост получает
   отказ без зависания (проверка таймаутов хоста), тест считается
   пройденным, если хост завершился сам за отведённое время.

**Критерий приёмки.** `hook_stress` зелёный 10 прогонов подряд локально
и в CI; аудит-лист с решениями по трём рискам включён в ARCHITECTURE.md;
ни один пункт не остался «неизвестно».

### Ф1.5 DllMain: зафиксировать контракт loader lock (P2, S)

**Проблема.** Анализ требует минимизировать работу под loader lock.
Фактически ключевой шаг уже сделан: тяжёлая установка inline-хука
выполняется в воркере (`v8i_export.cpp:1968-1977`), в DllMain — только
`IsTargetProcess` + `SetWindowsHookExW` + `CreateThread` (стартует после
выхода из loader lock) + `GetTickCount`. Осталось зафиксировать контракт,
чтобы он не был нарушен будущими правками.

**Шаги.**

1. В `dllmain.cpp` — блок-комментарий «Что разрешено в DllMain»:
   перечень разрешённых вызовов и правило «всё остальное — в воркер,
   который стартует после release loader lock». Ссылка на `V8iInstallCreateWindowThread`
   как образец.
2. Точечный аудит первых вызовов `V8iCbtProc` (в нём не должно быть
   загрузки модулей/файлового IO до первого «платформа устояла» —
   проверить и отметить).
3. Комментарий про `AppInit_DLLs` (`dllmain.cpp:10`) пометить как
   гипотетический сценарий загрузки (в репозитории путь не настраивается),
   чтобы не читался как действующая зависимость.
4. Раздел в ARCHITECTURE.md: «Фазы жизни payload: DllMain → воркеры →
   сессия v8i_probe», с указанием, что и в какой фазе может делать.

**Критерий приёмки.** Контракт задокументирован в коде и ARCHITECTURE.md;
поведение не изменяется; живая проверка ранней подписки на 8.5 по
VERIFY.md §F не регрессирует.

**Релиз этапа:** `v0.2.25` — сборка, ctest, `hook_smoke`, `hook_stress`,
живая проверка по VERIFY.md (инъекция, хуки, GitBar — разделы A–C).

1. Вынести из `v8i_export.cpp` все константы конкретных билдов:
   `kFrameVtblRva` (`:3375`), x86/x64 смещения `transmitCommand`
   (`:1100`), 8.5 `config.dll+0x2ED3B0` и slot-31 (`:2149`, `:2282`),
   `kConfigGroup` — в `data/builds/*.json`. В коде остаются только
   обращения через адаптер.
2. `platform_adapter.h`: `Detect(profiles)`, `FrameVtable()`,
   `TransmitCommand(...)`, `SubscribeEarly()`, `Validate(module, rva)`.
   Платформенные вызовы не выполняются без пройденной `Validate`.
3. **Вшивание профилей в бинарник**: payload в чужом процессе не должен
   зависеть от файлов на диске — CMake-генератор собирает
   `builds.inc` из `data/builds/*.json` (как уже сделано для иконок:
   `tools/gen_icons.py` → `icons.h`). JSON остаётся источником правки.
4. **Детект по сигнатурам**, не по номеру версии: перебор профилей,
   первый, чьи сигнатуры совпали по указанным RVA, и есть профиль
   (номер версии пишется в отчёт `cmdinfo` для человека). Это надёжнее
   парсинга `VS_VERSIONINFO` в чужом процессе.
5. Несовпадение сигнатур → операция отказывается с понятной ошибкой
   («билд не поддержан, профиль не совпал»), `cmdinfo` перечисляет, какие
   профили пробовались и что не сошлось. Никаких вызовов «на авось» по
   константе чужого билда.
6. Перенос — механический, без изменения поведения на поддержанных
   билдах; цепочка `cmd`/`cmd85` после переноса проверяется по VERIFY.md
   §D/§E на живой 8.3.27.1989 и 8.5.1.1529.

**Тесты.** Юнит: парсер профиля (валидный/битый JSON, отсутствие поля),
валидатор сигнатур на собственном PE-образе (приём из `unit_pe`), детект
из двух профилей на фикстурах. Живой: `cmdinfo` печатает выбранный профиль
и результат `Validate` на обеих платформах.

**Критерий приёмки.** `grep` не находит ни одной константы-адреса
конкретного билда вне `data/builds/` и `platform/`; на 8.3.27.1989 и
8.5.1.1529 всё работает как до переноса; на «чужом» билде команды
отказываются с внятной ошибкой вместо вызова по неверному адресу.

### Ф2.2 IPC: заголовок версии SharedIo (P1, M)

**Проблема.** Payload живёт в 1С до закрытия платформы; хост и GUI
обновляются раньше. Новый хост со старым payload в работающем процессе —
сегодня это немая порча раскладки памяти.

**Шаги.**

1. Правило структуры: **существующие поля `SharedIo` не двигаются**;
   новые добавляются только в конец. Это сохраняет совместимость со
   старым payload, который не знает о новых полях.
2. В конец добавляются: `uint32_t abiVersion`, `uint32_t magic`,
   `uint32_t caps` (резерв под разрешения этапа 4), `uint32_t reserved`.
   Хост заполняет их до `kStateIdle`.
3. Payload при подключении: старый — работает как раньше (новые поля
   не читает); новый — сверяет `abiVersion` и отказывается с новым
   diag-кодом `kDiagAbiMismatch`, по которому хост печатает
   «payload в процессе старой версии — перезапустите 1С или повторите
   внедрение». Старый payload против нового блока продолжает работать,
   пока раскладка головы не менялась — правило «только добавлять в конец»
   фиксируется в комментарии `protocol.h` и в чек-листе релиза.
4. Номер `abiVersion` инкрементится при **любом** изменении `SharedIo`;
   проверка версий вносится в чек-лист перед коммитом (plan_inj_ext §12)
   и в VERIFY.md.

**Тесты.** `unit_protocol`: блок с «чужим» `abiVersion` → `Client::Open`
отказывается с `kDiagAbiMismatch`; блок совпадающих версий работает как
сейчас (регресс).

**Критерий приёмки.** Смешанные версии дают понятную ошибку, а не мусор;
существующие тесты зелёные без правок логики.

### Ф2.3 Тестовый стенд: матрица совместимости и `check_cmd.sh` (P1, M)

**Проблема.** Анализ §4: юнит-тесты на искусственном процессе не
доказывают совместимость с Конфигуратором; нужен повторяемый сценарий для
`cmd`/`cmd85` с контролем отсутствия аварийного завершения. Закрывает
остаток A11.

**Шаги.**

1. `tools/check_cmd.sh` по образцу `check_gitbar.sh`: запустить 1С
   через `v8inject launch` → `cmdinfo` → `cmd 45` (8.3) / `cmd85 45`
   (8.5) → проверить (а) ответ с `rc=0` либо ожидаемую ошибку, (б)
   процесс 1С жив через 10 секунд после команды (контроль отсутствия
   аварийного завершения), (в) лог без `0xC0000005`-записей.
2. `docs/COMPAT.md` — матрица совместимости: строка на билд
   (8.3.27.1989 x86/x64, 8.5.1.1529 x64), колонки — группы возможностей
   (инъект/ранняя подписка, реверс-команды, хуки, cmd/cmd85, GitBar),
   значения — «проверено NNNN-NN-NN» / «не проверено» / «не поддержано».
   Обновляется после каждой живой проверки; в релизной заметке — ссылка.
3. Стенд: та же машина, где сегодня гоняется `check_gitbar.sh`, плюс
   зафиксированные копии платформ; в CI не переносится (осознанно —
   лицензии и вес платформы), шаг «живая проверка перед релизом»
   закрепляется в VERIFY.md как обязательный для релизов с правками
   payload.

**Критерий приёмки.** `check_cmd.sh` повторяемо зелёный на обеих
платформах; матрица заполнена фактическими датами; сценарий «команда
упала → процесс жив» покрыт отрицательным тестом (специально сломанный
профиль в отладочной сборке payload).

### Ф2.4 Синхронизация исследовательских документов (P2, S)

## 5. Этап 3. Архитектура (следующий цикл)

Цель: **контракт ответов, отзывчивый IPC и управляемые размеры модулей**.
Ветка `arch/*`, каждая фаза — серия механических PR.

### Ф3.1 Единый контракт ответов JSON (P1, M)

Закрывает остаток A7 и §3.3 (четвёртое) анализа.

**Контракт.**

```json
{ "status": "ok|error", "code": 0, "message": "", "data": {}, "seq": 42 }
```

- `seq` — из `SharedIo::seq` (уже растёт на каждый запрос) — связка
  «ответ ↔ запрос» для логов и GUI;
- `code` — машинный код ошибки (реестр в `protocol.h`); `message` — текст
  для человека; прежние поля ответа переезжают внутрь `data` без переименований.

**Шаги.**

1. Хелперы `OkEnvelope(data)` / `ErrEnvelope(code, message)` в
   `v8i_common` (рядом с `JsonEscape`), единая точка сборки.
2. Миграция группами по одной команде за коммит: реверс-команды →
   1С-команды (`cmd`/`cmd85`/`frames`) → gitbar/menu. На каждом шаге
   CLI/GUI читают новые ответы (правка парсинга ответа в cli/main.cpp и
   gui/main.cpp — тем же коммитом), старые поля в `data` сохраняются.
3. Тест диспетчера ужесточается: каждый ответ обязан иметь `status`,
   `code` и `seq` (сейчас проверяется только `status`).
4. `CLI.md` — раздел «Формат ответов» с реестром кодов.

**Критерий приёмки.** Ни один ответ диспетчера не обходится без конверта
(тест); CLI и GUI работают на новом формате; миграция не меняла смысловых
полей `data`.

### Ф3.2 IPC: событийная синхронизация (P2, M)

§3.3 (третье) анализа: опрос 15 мс → события.

**Шаги.**

1. Два именованных auto-reset события рядом с блоком:
   `Local\v8inject.<pid>.req` (host→payload) и `.res` (payload→host);
   создаются хостом с тем же SDDL, имя выводится из pid как у блока.
   Хендлы в SharedIo не кладутся (POD-only) — событие лишь говорит
   «посмотри на ready».
2. `Client::WaitForState`: fast-path опрос (как сейчас), затем
   `WaitForSingleObject(.res, остаток таймаута)`; перед ожиданием —
   повторная проверка состояния (закрывает гонку «сигнал ушёл до wait»:
   auto-reset + контроль state). Payload-сторона зеркально ждёт `.req`.
3. Тестовые стенды (`FakePayload`, `Dispatcher`) переводятся на ту же
   схему: они — вторая сторона, обязаны сигнализировать события.
4. Замер: в `unit_protocol` добавить проверку отклика < 100 мс на
   локальном блоке (сейчас цикл опроса может съедать до 15 мс).

**Критерий приёмки.** Все тесты зелёные; таймауты unchanged; отклик
на пустом блоке замеряется тестом; раскладка `SharedIo` изменилась
только добавлением в конец (см. Ф2.2).

### Ф3.3 Разбиение `v8i_export.cpp` (4277 строк) (P1, L)

Закрывает A40 и §3.4 анализа. Правило фазы: **только механический перенос,
ноль изменений поведения**, один PR на группу.

**Целевая структура** (по анализу, пути согласованы с payload-таргетом):

```
src/payload/commands/
  dispatcher.cpp         цикл V8iRunCommandLoop + таблица команд
  memory_commands.cpp    peek/find/findvalue/memmap/heapobjects/byhwnd
  pe_commands.cpp        pe/imports/exports/disasm/around/xref
  hook_commands.cpp      hook/hooks/unhook/trace
  platform_commands.cpp  version/cmdinfo/cmd/cmd85/frames/gitbar/menu/str
src/payload/platform/    — из Ф2.1
```

**Шаги.**

1. Сначала — общие зависимости: `PutResponse`, `Guarded`, глобальные
   `g_*` сгруппировать в `commands/shared_state.h` (POD-глобалы как есть,
   без «улучшений»).
2. Перенос по группам команд в порядке списка выше; после каждой группы
   — сборка обеих разрядностей + `ctest` + прогон диспетчер-теста.
3. Диспетчер (`dispatcher.cpp`) к концу — только маршрутизация; каждая
   группа — статические функции своего файла с минимальным интерфейсом
   (не тащить `g_*` наружу шире необходимого).
4. Ориентир: ни один файл этапа 3 не превышает ~1500 строк; контроль —
   строка «состав кода» в следующей ревизии AUDIT.md.

**Тесты.** Существующие `unit_dispatcher`/`unit_protocol` — главный
щит: если перенос что-то сломал, они покажут первым.

**Критерий приёмки.** `v8i_export.cpp` больше не существует либо
остался точкой входа экспортов (<300 строк); поведение на живой 1С
не изменилось (проверка по VERIFY.md §A–§D).

### Ф3.4 Разбиение `gitbar.cpp` (4143 строки) (P1, L)

## 8. Что осознанно не делаем

1. **Неограниченное выполнение произвольных команд через MCP** — против
   этого прямо направлена поправка анализа; в план не входит.
2. **Переписывание протокола с нуля** — SharedIo эволюционирует
   (заголовок ABI, события, конверт ответов), а не заменяется: слишком
   много кода и тестов уже держится на его раскладке.
3. **Новые функции GitBar до этапа 3** —god-файл 4143 строк нельзя
   расширять до разбиения (A40).
4. **Парсинг версии платформы из ресурсов в чужом процессе** — детект
   по сигнатурам (Ф2.1.4) проще и надёжнее.
5. **AppInit_DLLs как способ доставки** — путь не настраивается в
   проекте; комментарий в dllmain.cpp остаётся как гипотетический
   сценарий устойчивости, не как зависимость.
